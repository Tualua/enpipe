# Cross-AI Plan Review: Phase 10.1 — Программный декод в энкоде (qsvencc --avsw)

## 10.1-01

### Summary
Plan 10.1-01 implements the tracer path (`--decode hw|sw` → `chunk_command` → `qsvencc --avsw`), builds the D-09 harness (first/last frame verification via nearest-neighbor PSNR), and runs a VC-1 spike test to measure actual seek/trim behavior before any other work proceeds. This is the critical-path plan that must complete before 10.1-03 can wire up auto-resolution.

### Strengths
- **Single point of change verified**: `chunk_command` at `src/enpipe/encoding/chunk.py:44` is indeed the only place where `--avhw` appears — adding a `decode` parameter here is minimally invasive and correct.
- **Spike-first approach is correct**: The VC-1 Cues↔decode offset (RESEARCH.md shows +1/-1/0 non-constant differences) is the highest risk in the phase. Measuring it before writing resolution/wiring code prevents wasted effort.
- **D-09 harness design is sound**: `nearest_frame_verdict` with neighbor comparison catches the exact class of bug (silent ±1 frame shift with correct frame count). The existing `first_frame_verdict` at `_chunk_content.py:64-95` provides a proven pattern to follow.
- **Incremental `--decode` rollout**: Adding only `{hw, sw}` to `encode` (default `"hw"`) in this plan, deferring `auto` to plan 10.1-03, reduces blast radius and allows testing the mechanical path first.
- **Backward-compatible function signature**: `decode: str = "hw"` as last parameter with default preserves all existing callers (verified: `pipeline.py:223` calls with 6 positional args).

### Concerns
- **MEDIUM — `extract_frame_by_index` performance on large files**: The plan decodes from file start without `-ss` for frame N. For VC-1 with 63K frames at ~68 fps (RESEARCH.md), extracting frame 63000 means decoding ~15 minutes of video. The plan acknowledges this but doesn't mitigate. For the VC-1 spike (short cut) this is fine, but worth documenting as known slowness. (`_chunk_content.py:115-137` shows existing `_select_frame` has the same pattern with `-ss` fast path fallback.)
- **MEDIUM — Test compatibility across plans**: Tests written here (`test_run_encode_decode_sw_reaches_chunk_command`, `test_chunk_content_avsw_closed_gop`) use `--decode sw` explicitly. Plan 10.1-03 will change encode's default to `"auto"`. These tests should remain green since they pass explicit values, but the conftest stub added in 10.1-03 will need to not interfere.
- **LOW — `--va` compatibility with `--avsw` untested in this plan**: RESEARCH.md notes `--va` with `--avsw` on r4677/B50 is unverified. Plan Task 1's hardware test on synthetic HEVC will prove basic compatibility, but edge cases (e.g., 10-bit input) aren't covered until real VC-1 runs.

### Suggestions
1. In `extract_frame_by_index`, consider a mid-point optimization: if N > total/2, decode from end with `-sseof` and count backwards. Not required for correctness but would help UAT on full Fringe S02E01.
2. Add a `nearest_frame_verdict` test case for the "tie" scenario where PSNR to center equals PSNR to neighbor — current `<behavior>` specifies this should error, which is correct.

### Risk Assessment: **LOW**
The plan is well-scoped, correctly identifies the highest risk (VC-1 seek/trim offset), and uses checkpoint:decision before committing to any compensation code. The tracer path is minimal and verifiable.

## 10.1-02

### Summary
Plan 10.1-02 creates the leaf module `enpipe.shared.decode` containing: (1) pure functions for parsing `qsvencc --check-features` output into a decode capability table, (2) pixel format classification, (3) auto-resolution logic with fail-closed semantics, (4) ffprobe-based video format probing, and (5) CLI argument decoding with `--no-qsv` deprecation handling.

### Strengths
- **Follows proven pattern exactly**: The `query_hw_decoders()` / `resolve_decode()` design mirrors `ensure_qsvencc_fixed()` at `src/enpipe/shared/qsvencc_version.py:92-123` — same OSError/TimeoutExpired handling, same `die()` on failure, same "no cache" philosophy. This consistency reduces review burden.
- **Fail-closed by design**: Every ambiguity (unknown `pix_fmt`, parse failure, missing qsvencc, timeout) results in `die()` with actionable message. No fallback lists, no guessing. This matches project Core Value ("correctness is non-negotiable").
- **(codec, chroma, depth) key is correct**: RESEARCH.md proves H.264 on B50 only supports yuv420 8-bit. Using bare `codec_name` would send Hi10P AVC to `--avhw` and silently fail. The D-14 decision is validated by evidence.
- **`field_order` check before qsvencc query**: Checking interlaced status (via ffprobe, no external process needed) before the ~4s `qsvencc --check-features` call saves time when we'd die anyway.
- **Truly leaf module**: No imports from `detection`, `encoding`, or `analysis`. Only `stdlib`, `enpipe.shared.proc`, `enpipe.shared.logging`. This keeps dependency graph acyclic as required.

### Concerns
- **HIGH — `detect --decode auto` introduces qsvencc dependency**: Currently `run_detect` at `src/enpipe/detection/pipeline.py:29` has NO tool preflight (explicitly documented at lines 7-13: "в отличие от run_encode, здесь НЕТ shutil.which-preflight"). After this plan, `detect --decode auto` will call `resolve_decode` → `query_hw_decoders()` → `qsvencc --check-features`. If qsvencc is not in PATH, detect now fails. This is a **behavior change** for users who currently run `detect` without qsvencc installed. The plan acknowledges this in Task 2 action item 2 ("явно отразить в тексте отказа") but the impact should be clearly communicated — it breaks the documented invariant that detect stage has no tool preflight.
- **MEDIUM — No cache for `query_hw_decoders()`**: Plan explicitly decides against caching (~4s per call). In batch mode with many files, e.g., 50 files × 4s = 200s of redundant qsvencc queries. The `ensure_qsvencc_fixed` parallel is noted (also no cache, ~7ms per call), but 4s vs 7ms is a 500× difference. Consider `functools.lru_cache(maxsize=1)` with `cache_clear()` in tests — the plan mentions this as "решение планировщика" and chooses against it, but the cost is non-trivial for large batches.
- **LOW — Fixture file fragility**: `check_features_b50_r4677.txt` must be byte-exact including trailing whitespace. Any editor reformatting or line-ending change breaks it. The plan correctly warns about this, but CI should add a verification step (e.g., `file` command or git attributes).
- **LOW — `pix_fmt_format` coverage**: Behavior list includes `yuvj420p→("yuv420",8)` and `gray→None`. Real-world formats like `yuv420p16le` (16-bit), `nv12` (NV12 semi-planar), `rgb24` are correctly rejected. But what about `0rgb` / `bgr0` (packed RGB from some captures)? These would hit `None` → `die()`, which is fail-closed and correct.

### Suggestions
1. Add a comment in `detection/pipeline.py` docstring noting that `--decode auto` adds a qsvencc dependency that didn't exist before — this helps future maintainers understand why detect fails without qsvencc.
2. Consider adding `lru_cache` behind a feature flag or environment variable if batch performance becomes problematic — the no-cache decision can be revisited without API changes.

### Risk Assessment: **MEDIUM**
The module design is solid and follows established patterns. The primary risk is the behavioral change to `detect` (new qsvencc dependency for `--decode auto`), which could surprise existing users. The fail-closed properties are excellent.

## 10.1-03

### Summary
Plan 10.1-03 wires the decode resolution module from 10.1-02 into all three CLI entry points (`detect`, `encode`, `run`), implements `--no-qsv` as deprecated synonym for `--decode sw` with mutual exclusion, ensures single-decision-per-file in `run` (passed by value to both stages), and adds the necessary test stubs and conftest autouse fixture.

- **Batch mode correctly resets decision**: `process_one` rebuilds Namespace with `"decode_choice": None` (plan action item 1, batch branch), so each file gets its own resolution. This satisfies D-05.
- **Backward compatibility via getattr**: `getattr(args, "decode", "hw")` and `getattr(args, "decode_choice", None)` ensure existing test Namespaces (built manually without these fields) continue to work. Verified: `test_pipeline_wiring.py:33-37` builds Namespace without `decode`.
- **Conftest stub follows proven pattern**: `_stub_resolve_decode` patches the same three import sites as `_stub_qsvencc_gate` (`tests/unit/conftest.py:27-32`): `enc_pipeline`, `cli_main`, and now also `det_pipeline`. Docstring explains why.

### Concerns
- **HIGH — `use_qsv` derivation change**: Current code at `src/enpipe/detection/pipeline.py:63`: `use_qsv=not args.no_qsv`. New code: `use_qsv=(choice.path == "hw")`. When `--no-qsv` is set, `decode_mode_from_args` returns `"sw"` → `choice.path == "sw"` → `use_qsv=False` — same result. **But** when `--decode auto` resolves to `sw` (e.g., VC-1), `use_qsv` becomes `False` even though `no_qsv` is `False`. Existing tests that assert on `use_qsv` based solely on `no_qsv` may need updating. The plan's `<behavior>` section covers this, but it's a subtle semantic shift.
- **MEDIUM — Three import sites for stub synchronization**: The conftest stub must patch `enc_pipeline.resolve_decode`, `cli_main.resolve_decode`, and `det_pipeline.resolve_decode`. If a future refactoring changes where these are imported from, the stub silently stops working and tests fail with cryptic "qsvencc not found" errors (the fail-closed die fires). The existing `_stub_qsvencc_gate` has the same risk (2 sites), so this is known, but 3 sites increases surface area.
- **LOW — `--no-qsv` help text deprecation only**: The flag still works identically; only `--help` text changes. Users with scripts using `--no-qsv` see no breakage. The mutual-exclusion check (`--no-qsv --decode hw` → SystemExit) is new and correct.

### Suggestions
1. Add an explicit test: `Namespace(no_qsv=True, decode="auto")` → `decode_mode_from_args` returns `"sw"` (verifying D-06: `--no-qsv` overrides `--decode auto`).
2. In `run_detect`, log the decode choice to stderr (not stdout) to match existing start/finish lines (lines 75-80 of `detection/pipeline.py`). The plan does this correctly.

### Risk Assessment: **LOW-MEDIUM**
The wiring is straightforward and follows existing patterns. The main risk is the `use_qsv` semantic shift, which is well-documented in the plan and covered by tests. Dependency ordering (depends on 10.1-01 and 10.1-02) is correct.

## 10.1-02

**Summary:** Plan 02 builds the leaf decision module `enpipe.shared.decode` with a clean separation between pure parsing (table, pix_fmt, auto_path, check_progressive) and subprocess-backed operations (query_hw_decoders, probe_video_format, resolve_decode). **Strengths:**

- The `check_progressive` function correctly implements D-13: refuse only on `tt/bb/tb/bt`, treat `None`/`unknown`/`progressive` as progressive. This matches the existing policy at `src/enpipe/analysis/precheck.py:350`.
- The module is correctly leaf-shaped: imports only `enpipe.shared.proc` and `enpipe.shared.logging`, no circular dependencies with `detection` or `encoding`.
- The fixture approach (`check_features_b50_r4677.txt`) with a precondition to capture from real hardware is excellent — prevents hand-crafted fixtures that might not match real output.

**Concerns:**
- **MEDIUM — `query_hw_decoders` cost in batch mode:** The plan explicitly decides against caching ("~4 с на файл против минут энкода, без состояния модуля"). For a batch of 20 files, this adds ~80 seconds of pure overhead. While not a correctness issue, the plan should note this in the SUMMARY so the operator can make an informed decision later. The comparison with `ensure_qsvencc_fixed` ("~7 мс") is misleading — that one is fast because it only runs `qsvencc --version`, not `--check-features`.
- **MEDIUM — `probe_video_format` error message quality:** The plan says "rc≠0, нет streams или нет codec_name → die с именем файла и stderr ffprobe (последние ~300 символов)". - **LOW — `auto_path` reason strings:** The plan specifies example reasons like "vc1 нет среди аппаратных декодеров GPU" and "h264 yuv420 10 бит: GPU декодирует H.264 yuv420 только до 8 бит". These are clear, but the `describe_decode` format `"декод: {path} ({reason}; --decode {mode})"` could produce long lines. Not a blocker, just a cosmetic note.
- **LOW — `DECODE_MODES` tuple vs frozenset:** The plan uses `Tuple[str, ...]` for `DECODE_MODES`. Since it's used for `choices=list(DECODE_MODES)` in argparse, a tuple is fine, but a frozenset would better communicate "unordered set of valid values". Minor style point.

**Suggestions:**
- The `parse_decode_table` should have a test case where the header contains an unknown codec column (e.g., "XYZ") mixed with known ones — the plan's "ни одной известной колонки → None" rule should be tested at the boundary (1 known + 1 unknown → should still parse).
- Consider adding a `__all__` or at least a docstring section listing the public API surface, since this module will be imported from multiple places.

**Risk Assessment:** LOW — the module is well-isolated, the parsing algorithm is verified against real output, and the fail-closed behavior is consistent with the project's established patterns.

## 10.1-04

## Consensus Summary

Оба ревьюера работали с доступом к репозиторию и ссылаются на `file:line`. Общая оценка — MEDIUM. Оба считают верными порядок волн (01+02 → 03 → 04), подход «сначала спайк VC-1» и отказ по умолчанию при любой неясности.

### Agreed Strengths
- Сначала спайк `--avsw --seek/--trim` на VC-1, а `checkpoint:decision` не выбирает стратегию за оператора (10.1-01).
- `chunk_command` — единственное место с `--avhw` (`src/enpipe/encoding/chunk.py:44`); новый параметр `decode="hw"` по умолчанию оставляет существующие вызовы позиционными и зелёными (`src/enpipe/encoding/pipeline.py:223`).
- `enpipe.shared.decode` построен по образцу `ensure_qsvencc_fixed` (`src/enpipe/shared/qsvencc_version.py:92-123`), это листовой модуль без циклов. Ключ (кодек, цветность, разрядность) обоснован таблицей B50 (D-14).
- Одно решение на файл передаётся по значению в детект и энкод; в батче `decode_choice` сбрасывается для каждого файла (D-05).
- Три ветки 10.1-04 исполняются строго по `decision:` из SUMMARY; в ветке refuse-handoff стоит `xfail(strict=True)`, который сработает, когда выйдет фикс форка.

### Agreed Concerns
1. **HIGH (оба) — `enpipe detect` получает зависимость от qsvencc.** Сейчас `run_detect` намеренно работает без preflight (`src/enpipe/detection/pipeline.py:7-13`). При дефолтном `--decode auto` detect вызовет `qsvencc --check-features`, и без qsvencc в PATH упадёт. Это изменение поведения. Предложения: явный preflight или понятный отказ с подсказкой `--decode hw|sw`, тест на отсутствие qsvencc, запись в docstring/документации.
2. **MEDIUM (оба) — нет кэша опроса декодеров в батче.** Опрос стоит около 4 с на файл, это примерно в 500 раз дороже `--version` (~7 мс). Сравнение с `ensure_qsvencc_fixed` вводит в заблуждение. Предложение: `lru_cache(maxsize=1)` на процесс либо хотя бы явная запись компромисса в SUMMARY.
3. **MEDIUM/HIGH (оба) — ветка `compensate` — тупик для фазы.** Цель (кодирование Fringe) в ней не достигается, нужно gap-планирование. Оба считают это корректным, но просят явно указать, что фаза остаётся незакрытой.
4. **MEDIUM (оба) — семантика `use_qsv` в детекте.** Значение `use_qsv` теперь выводится из `choice.path`, а не из `no_qsv`; нужен тест, что `decode_choice` главнее `no_qsv` и что `--no-qsv` перебивает `--decode auto`.

### Divergent Views
- **OpenCode:** в ветке refuse-handoff заранее отвергать и `--decode hw` на VC-1 — иначе qsvencc упадёт с непонятной ошибкой. Ещё: `extract_frame_by_index` медленно работает на больших файлах (декод от начала), а в UAT стоит указать ожидаемое время (~15 мин детекта плюс энкод).
- **Qwen:** перед повторным использованием в 10.1-04 проверить, что пересозданный mkvmerge-кусок детерминирован (sha256). Также сообщение об ошибке `probe_video_format` должно содержать argv ffprobe, а интеграционный тест — проверять, что строка лога декода выводится ровно один раз и что явный `--decode sw` не опрашивает qsvencc.
