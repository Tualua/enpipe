# Phase 10.1: Code Review Report

**Reviewed:** 2026-11-11
**Depth:** standard
**Files Reviewed:** 19

## Summary

Phase 10.1 adds the per-file `--decode auto|hw|sw` choice, with a VC-1 refusal on the `--avsw` path. I traced the decision flow through `run`, `encode`, `detect` and batch mode. I found no critical defect.

- **Single decision per file:** `_pipeline_one` resolves the decision once and passes the same `decode_choice` object to both stages. The batch branches in `run_detect` and `run_encode` reset `decode_choice=None`, so no decision leaks from one file to the next.
- **Refusal coverage:** `refuse_unsafe_avsw` runs in `_pipeline_one` before detect, and in `run_encode` for both a pre-made choice and a fresh one. It runs before the workdir is created. Explicit `--decode sw` and `--no-qsv` do not bypass it.
- **`--check-features` parsing:** it fails closed on every error path I looked at. These are a missing binary, a timeout, a non-zero rc, a missing section header, an unrecognised column set, a row that does not start with `yuvNNN`, an unaligned cell, and a tie between two columns. The only fail-open direction is a missing cell, which means "no hardware decode" and so selects the safe `sw` path.
- **Remaining gaps:** the refusal covers a single ffprobe codec name, and one wiring default is silently `hw`. The new strict-xfail VC-1 test can mask unrelated failures. The content gate has a blind spot on low-motion footage.

## Warnings

### WR-01: VC-1 refusal covers only `codec_name == "vc1"`; the other VC-1 family members and unvalidated software-only codecs reach `--avsw`

**File:** `src/enpipe/shared/decode.py:60` (`AVSW_UNSAFE_CODECS`), `src/enpipe/shared/decode.py:139` (`auto_path`)
**Issue:** The silent ±1 frame shift was measured on VC-1 only (spike 10.1-05).
- ffprobe reports Windows Media Video 9 (VC-1 Simple/Main profile) as `wmv3`, and the image variant as `vc1image`. They are not in the set, so they get through.
- `wmv3` has no column in `CODEC_COLUMNS`, so `auto` routes it to `sw` with no refusal. If the shift comes from the VC-1 decoder in libavcodec, `wmv3` has the same defect.
- `mpeg4`, `msmpeg4v3`, `wmv2`, `mjpeg` and every other codec outside the table are also sent to `--avsw` by `auto` without any content validation. This is the "silent output corruption" risk the project treats as primary.
- `test_unsafe_codecs_is_vc1_only` locks in the narrow set, so a future fix would have to change the test.

**Fix:** At minimum extend the set and update the test:
```python
AVSW_UNSAFE_CODECS = frozenset({"vc1", "wmv3", "vc1image"})
```
Better, invert the policy: `auto` sends a codec to `sw` only if it is in an explicitly validated allowlist (for example mpeg2video, h264, hevc, vp9, av1 on the `sw` path). Any other codec dies with the `--decode hw|sw` hint, which matches the D-04 fail-closed philosophy.

### WR-02: `chunk_command(decode="hw")` default silently picks the hardware path

**File:** `src/enpipe/encoding/chunk.py:28`
**Issue:** There is exactly one production caller. Any future caller, or any test double that does not forward `decode`, silently gets `--avhw` regardless of the per-file decision. `test_pipeline_wiring.py` even asserts "Namespace without a decode field -> old hw path for all chunks". The wiring defect "wrong decode path reaching qsvencc" therefore has a quiet failure mode. The `ValueError` guard handles only bad values, not an omitted argument.
**Fix:** Make the parameter required (keyword-only, no default):
```python
def chunk_command(src, seek, trim, out, hdr_flags, metrics, *, decode: str) -> List[str]:
```
Update the test doubles in `test_pipeline_wiring.py` and `test_chunk.py` to pass it.

### WR-03: `@pytest.mark.xfail(strict=True)` without `raises=` makes `test_chunk_edges_avsw_vc1` pass on any failure

**File:** `tests/integration/test_hardware_real_media.py:1463` (decorator), body at 1470-1545
**Issue:** The test is meant to document the known VC-1 content shift, but a strict xfail with no `raises` turns every failure into "expected".
- Examples are a `pytest.fail("precondition: ...")`, a `CalledProcessError` from ffmpeg, a broken `_decode_pict_types`, a `KeyError`, or a regression in `chunk_command`.
- All of these are reported as XFAIL, so the test cannot tell "VC-1 still shifts" from "the test is broken".
- The only signal is an XPASS, which fires only if everything incidentally passes.
- The `diff_of`/`picked` preconditions are especially exposed, because they depend on an operator-supplied file.

**Fix:** Restrict the xfail to the content assertion, for example `raises=AssertionError`. Move preconditions and ffmpeg errors out of that exception type (use `pytest.skip` or `RuntimeError`). Alternatively, run the verification, collect the errors, and call `pytest.xfail(...)` only when the errors are content mismatches.

### WR-04: `nearest_frame_verdict` ignores neighbours that are close to the centre, so a one-frame shift on low-motion footage passes the gate

**File:** `tests/integration/_chunk_content.py:105-143`
**Issue:**
- A neighbour is considered only if `src_nb < q - MARGIN_DB`, where `q` is the maximum of the chunk PSNRs. In slow or static scenes the adjacent source frames are within 3 dB of `q` and are skipped.
- A chunk shifted by exactly one frame, with a correct frame count and rc=0, then passes. The test claims to detect exactly that.
- `disc_first == 0 or disc_last == 0` fails the run only when no chunk at all was discriminating. One high-motion chunk makes the whole run non-vacuous even if the other chunks were never really checked.
- The `(37.0, {1: (36.5, 34.0)})` case, with a PSNR gap of 0.5 dB, is not covered by the tests.

**Fix:**
- Report the number of non-discriminating chunks per edge, and fail or warn when the fraction exceeds a threshold.
- For non-discriminating edges, use a stricter secondary check that does not rely on the source-source PSNR gap, for example an exact (SSIM or per-pixel) compare of the first intra frame against all candidates.
- Add a unit test for the near-tie case.

## Info

### IN-01: Local variable `mode` is rebound to an unrelated value in `run_detect`

**File:** `src/enpipe/detection/pipeline.py:43` and `src/enpipe/detection/pipeline.py:106`
**Issue:** `mode = decode_mode_from_args(args)` holds the decode mode and is used at line 80. Further down, `mode = "параллельный" if ... else "последовательный"` rebinds it to a log label. This works today, but any later reuse of `mode` between the two (or a refactor that moves the resolve below the label) would silently pass the wrong string to `resolve_decode`.
**Fix:** Rename one of them, for example `decode_mode` and `jobs_label`.

### IN-02: `--no-qsv` on `run` now changes the encoder's decode path, not only detection

**File:** `src/enpipe/cli/main.py:62-70` (`_pipeline_one`), `src/enpipe/shared/decode.py:157` (`decode_mode_from_args`)
**Issue:** Before this phase, `enpipe run --no-qsv` affected the detector only. It is now a synonym for `--decode sw`, so the encode stage runs `qsvencc --avsw` too. This is per D-06 and documented in the help text, but it is a silent behavioural change for existing scripts and cron jobs. `encode` has no `--no-qsv`, so the only way to keep the old behaviour is `--decode hw` with a separate detect step.
**Fix:** No code change is needed if D-06 is intentional. Consider logging a one-line deprecation notice when `--no-qsv` is used, and mention the change in the release notes.
