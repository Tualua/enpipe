Механизм проверен при планировании на закреплённом ffmpeg n9.0.2 (BtbN, /usr/local/bin) в devcontainer; libx265, libsvtav1, фильтр showinfo и /usr/bin/mkvmerge присутствуют.

1. Воспроизведение RASL: источник как `src_cfr` медиа-теста (testsrc2 640x360@24, 4 c, x265 `bframes=4:keyint=48:open-gop=1`, yuv420p10le) → `mkvmerge -q -o cut.mkv --split timestamps:2s src.mkv` даёт `cut-001.mkv` и `cut-002.mkv`. У `cut-002.mkv` 50 пакетов, но framemd5 даёт 48 кадров; первые пакеты: `0.083 K`, `0.041`, `0.000` (два RASL, pts меньше CRA); ffprobe stream/format start_time = 0.083. Отсортированная таблица: [0.000, 0.041, 0.083, …] — индексы 0 и 1 не декодируются.
2. Без seek (n = 0) текущий grab отдаёт CRA (pts 0.083) как «кадр 0» — подмена.
3. showinfo (печатает на уровне info) даёт строки `[Parsed_showinfo_0 @ 0x…] config in time_base: 1/1000` и по кадру `[Parsed_showinfo_0 @ 0x…] n:   0 pts:     21 pts_time:0.021 …` (за ними длинные строки side data/SEI — их пропускать). Строк кадров приходит count + 1 (фильтр получает лишний кадр до остановки -frames:v) — брать первые count.
4. С `-seek_timestamp 1 -ss SS` (без -copyts) ffmpeg вычитает ровно SS: абсолютный pts = pts_int · time_base + SS. Проверено: st.mkv (start 2.5), n=10, SS=2.896 → showinfo 0.021 → 2.917 = pts[10]; cut-002, n=2, SS=0.062 → 0.021 → 0.083 = pts[2]; cut-002, n=1, SS=0.0205 → 0.062 → 0.0825 ≈ CRA ≠ pts[1] = 0.041 (расхождение ловится).
5. Без -ss вывод нормирован на start_time входа, который у RASL-нарезки = 0.083 (а не pts[0]) — поэтому для n = 0 нужен `-copyts` (без -ss): тогда showinfo печатает абсолютные pts (cut-002 → 0.083; st.mkv → 2.5; src.mkv → 0), а байты кадров идентичны прежним (md5 совпали). `-copyts` вместе с `-ss` НЕ использовать: проверено, что так ffmpeg выбирает не те кадры (st.mkv n=10 → 5.417).
6. pts_time печатается с %.6g (теряет точность на длинных фильмах) — считать по целому `pts:` и time_base, а не по pts_time.
