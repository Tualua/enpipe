# Ревью планов Phase 10: Извлечение кадров и выравнивание

## 1. Итог (Summary)

Планы высокого качества: опираются на экспериментально проверенное исследование (все ключевые факты о `-seek_timestamp 1`, pts-таблицах, поведении `avg_frame_rate` верифицированы в сессии), строго следуют конвенциям проекта (чистое ядро + тонкий I/O, worker-контракт `(result, err)`, шов `shared.proc`, fail-loud без `die()`), и все 5 критериев успеха ROADMAP действительно закрываются планами. Разбиение на волны корректно: 10-01 фиксирует контракты до параллельной реализации 10-02/10-03 (файлы не пересекаются), 10-04 собирает всё, 10-05 выносит на оператора то, что невозможно проверить в контейнере. Основной остаточный риск — не технический, а калибровочный: порог 3 дБ и правило склеек без повторных точек могут давать ложные отказы на реальном малоподвижном контенте; это осознанно помечено provisional и проверяется в UAT, но стоит явного внимания.

## 2. Сильные стороны

- **Interface-first (10-01)**: имена и сигнатуры зафиксированы дословно до реализации, параллельные планы 10-02/10-03 пишут против готовых контрактов без правок общих файлов — правильная механика для волн.
- **Анти-флейк дизайн медиа-теста (10-04)**: отдельная проверка запаса фикстуры сдвига, запасной вариант (шум + crf 20) вместо снижения порога, grep-гейт на `align_margin_db < 3` — редкая по качеству защита от «зелёных тестов ценой ослабления инварианта» (T-10-20).
- **Явная обработка ловушек из исследования**: `inf − inf = nan` на статике (ничья проверяется до вычитания), обрезанное окно ≠ «сдвиг ≥ W», `-seek_timestamp 1` при start_time ≠ 0, сортировка pts (порядок декода ≠ порядок показа), `N/A`-pts → отказ по D-02.
- **Изоляция пакета**: сторож обновлён точечно (allow-list только для `frames.py`, только на `enpipe.shared`/`enpipe.shared.proc`, с самопроверками `test_checker_allow_does_not_cover`) — обход изоляции закрыт тестом (T-10-03).
- **Границы фазы железные**: acceptance-критерии `git diff --stat -- src/enpipe/encoding …` пусты, DV/подсказка-offset/рендер отказа — данными модели, а не побочными эффектами; CLI сознательно отложен в фазу 11.
- **Кэш pts (D-21)**: JSON вместо pickle, ключ идентичности (path, size, mtime_ns), атомарная запись `tmp + os.replace`, ошибка записи не валит анализ, инвалидация покрыта fp-тестами.
- **Открытые вопросы RESEARCH не потеряны**: каждый (jobs/threads, теги A8, модель отчёта) привязан к конкретной задаче конкретного плана с правилом принятия решения.

## 3. Замечания (Concerns)

- **[MEDIUM] Склейки без повторных точек — риск ложных отказов на реальном контенте.** `retry_frames` применяется только к не-склейкам (D-11 — про случай без `.scenes`). С `.scenes` все 5 точек — склейки; если ≥ 3 из них попадут на малоподвижные/статичные сцены (запас < 3 дБ), файл получит отказ «неопределённо» без единой попытки другой точки. Правило D-13 допускает до 3 «неопределённо», но на длинном фильме с тихими сценами это реально. Смягчено (provisional, UAT 10-05 шаг 1 покажет на реальной паре, калибровка фаза 13), но в 10-02-SUMMARY стоит зафиксировать это как известное ограничение явно.
- **[MEDIUM] Допущение framemd5 == md5(склеенных плоскостей) обосновано только эмпирически.** Сверка `Y.tobytes()+U.tobytes()+V.tobytes()` с хешем `framemd5` работает, потому что framehash хеширует упакованные данные плоскостей без stride-паддинга — это проверено на n9.0.2, но нигде в плане не зафиксировано как допущение. При смене ffmpeg (сейчас pinned — ОК) тест молча перестанет быть валидным или упадёт непонятно почему. Стоит одной фразы в docstring теста.
- **[MEDIUM] Память воркера при `align_window = 8`.** MAX_GRAB_FRAMES = 18 при 4K ≈ 331 МБ на воркер; при jobs=2 и окне склейки это ~660 МБ только на окна источника. Threat model 10-04 оценивает «~130–150 МБ» для дефолтного W=3, но потолок конфига до 8 не оценён. Низкая вероятность (дефолт 3), но либо сузить ALIGN_WINDOW_MAX, либо дописать оценку в threat model.
- **[MEDIUM] `pick_points` через float и `round()` (banker's rounding).** Для align_points=5 делитель 4 — точный в binary, поведенческие тесты сходятся. Но при points=6 (или ином) `i·(n−1)/(points−1)` даст нерепрезентимые половины и флейпы. Целочисленная формула `(i·(n−1) + (points−1)//2) // (points−1)` дешевле и детерминированнее.
- **[LOW] Отрицательные pts не покрыты.** Некоторые контейнеры дают отрицательные `pts_time`; `sorted()` их переживёт, но поведение `-ss` с отрицательным значением и `-seek_timestamp 1` не тестировалось. Либо явный отказ в `pts_reasons` (min(pts) < 0 → причина), либо тест-кейс.
- **[LOW] Interlace не проверяется.** Из probe-ENTRIES в 10-03 выпало `field_order` (было в RESEARCH). AV1-энкод прогрессивный, но чересстрочный HEVC-источник молча пройдёт предпроверку. Достаточно пометки «не поддерживается» в docstring, либо причины отказа.
- **[LOW] Медиа-тест попадает в дефолтный тир `pytest -q`.** ~60 с к каждому прогону. Маркер добавить нельзя (pyproject.toml в списке «не менять») — это осознанный компромисс, но в SUMMARY стоит записать фактическое время и решение по нему.
- **[LOW] 10-05 проверяет A8 только по четырём color-тегам.** HDR10+/DV 8.1-метаданные энкода (RPU-путь) вне проверки — приемлемо для D-17, но упомянуть в SUMMARY, что «проходит как обычный PQ» проверяется только тегами.

## 4. Предложения (Suggestions)

- В `align.pick_points` перейти на целочисленную арифметику целей; добавить тест на points=6.
- Зафиксировать в docstring `test_seek_matches_framemd5` допущение «framemd5 хеширует упакованные плоскости без паддинга (проверено на n9.0.2)».
- Рассмотреть fallback для склеек: если склейка «неопределённо», одна повторная попытка соседним равномерным кадром (конфигурируемая, дефолт выкл.) — кандидат в фазу 13, но место в `AlignTarget`/`_point_worker` для этого стоит оставить.
- В `check_pair` добавить явную причину для не-прогрессивного источника (`field_order`/`coded_content`), если решите возвращать его в ENTRIES — иначе записать ограничение в docstring.
- В 10-05 скрипт добавить печать пиковой памяти процесса замера (`ru_maxrss`) — дешёвая проверка оценок из threat model 10-04.
- В `combine_junction` уточнить в docstring поведение `margin_db`, когда одна из двух точек `undetermined` (сейчас «минимум определённых» — допустимо, но недокументировано).

## 5. Оценка риска

**MEDIUM** (близко к LOW).

Обоснование: техническая база — самая сильная часть: все критичные факты о seek/pts/декоде верифицированы экспериментально в исследовании, быстрый и медиа-тиры дополняют друг друга, инвариант «отказ при любом сомнении» продублирован на уровнях предпроверки, точки, кадра и файла, а главный исторический риск проекта (тихая порча вывода) покрыт grep-гейтами и санити-проверками запаса. Остаточный риск сосредоточен в одном месте — **калибровке вердикта на реальном контенте** (порог 3 дБ, склейки без повторов), и он по конструкции не может дать ложного «выровнено» — только ложный отказ, который UAT 10-05 и фаза 13 должны поймать до того, как это станет проблемой пользователя. Ни один план не требует недоступных зависимостей, не трогает путь кодирования и не ослабляет существующие инварианты.

- Точечная allow-list в стороже изоляции с самопроверками (`test_checker_allow_does_not_cover`) — защита от расширения лазейки.

### Замечания
- **LOW.** Task 1 объединяет 10 новых полей `AnalyzeConfig`, 6 новых датаклассов/констант в `model.py`, модульные константы и обновление тестов — это большой атомарный коммит. При ошибке в одном поле `__post_init__` пересобирается весь Task. Разбиение на два task (сначала config.py + константы, потом model.py + датаклассы) снизило бы риск, но увеличивало бы число файловых конфликтов. Текущий вариант приемлем, если исполнитель прогонит verify после каждого подшага.
- **LOW.** `MAX_GRAB_FRAMES = 2 * ALIGN_WINDOW_MAX + 2 = 18` — формула верна для окна склейки (кадры `start−1` и `start` ± W = 2·(W+1) = 2W+2 при W=8 → 18), но в 10-04 `_point_worker` для обычной точки (не склейки) использует окно `2W+1 = 7`. Константа 18 покрывает оба случая, но это неочевидно из имени. Рекомендую добавить комментарий в config.py с пояснением, что 18 — потолок на склейку, обычная точка укладывается в 7.
- **LOW.** В behavior `test_build_thresholds_distinct_values_and_types` перечислены 10 новых полей с конкретными альтернативными значениями. Если исполнитель подставит значения, случайно совпадающие с дефолтами другого типа (например `align_window=3.0` вместо `4`), тест не поймает. Стоит добавить в read_first явное указание: «значения того же типа, что и дефолт (int→int, float→float)».

## 10-02-PLAN.md — Чистое ядро

### Сильные стороны
- Явная обработка `inf == inf` (статика) и ничьи **до** вычитания — ключевая находка исследования (Pitfall 4) закреплена в контракте.
- `offset_hints` через двухуказательное окно O(n) по префиксным суммам — эффективно и элегантно.
- Правило «ошибка извлечения в точке = причина отказа, а не неопределённо» — правильная ужесточающая семантика (D-13 «отказ при любом сомнении»).
- `combine_junction` для склеек с правилом A5 (start−1/start) и `frame_verdict` = `point_verdict(window=1)` для D-14 — минимальный код, максимальное переиспользование.

### Замечания
- **MEDIUM.** `pick_points` с добором равномерных точек, если склейка уже занята другой целью, описан текстом, но не формализован. Пример behavior: `pick_points(96, scenes 4×24, offset 0, cfg points 5)` → цели `round(i·95/4)` = 0, 24, 48, 72, 95; склейки 0, 24, 48, 72 уже покрыты; цель 95 → ближайшая склейка 72 уже занята → берём 95 как равномерную. Это работает, но алгоритм «ближайшая склейка (ничья — более ранняя)» может дать неожиданный результат при нечетном числе точек и несимметричных сценах. Рекомендую добавить в behavior тестовый случай с 3 точками и сценами (0,10),(10,20),(20,96) — проверить, что цели 0, 48, 95 дают склейки 0 и (48→ближайшая 20 или 96?) и равномерную.
- **MEDIUM.** `point_verdict`: «при равных psnr — по |d|» для детерминизма. Но если `psnr(d=−1) == psnr(d=+1)` и оба конечные — это реальный случай симметричного контента (например, статичный объект на фоне). Алгоритм выберет d=−1 (меньший |d| при ничьёй? или первый по сортировке?). Нужно уточнить: `isclose` проверяется между **лучшим и вторым**, а не между всеми парами. Если `psnr(−1) = 40.0` и `psnr(+1) = 40.0` — это ничья → undetermined. Но если `psnr(−1) = 40.0`, `psnr(0) = 39.9999999` — `isclose(rel_tol=1e-9)` может дать True или False в зависимости от порядка. Рекомендую зафиксировать: сортировка `(psnr, -|d|)` по убыванию, `isclose` между первыми двумя элементами после сортировки.
- **LOW.** `detect_vfr` в `precheck.py` (Task 2) использует медиану зазоров. При чётном числе зазоров медиана — среднее двух средних. Это стандартное поведение, но на фикстуре из 4 кадров (3 зазора) медиана = второй зазор. Тест должен это учитывать.
- **LOW.** `check_pair` проверяет `format_name` на наличие "obu" через `split(",")`. Но `StreamInfo.format_name` приходит из ffprobe `format=format_name` — для `.obu`-файла это может быть `"obu"` или `"rawvideo"`. Plan покрывает только `format_name`, но не имя файла (`name`). В behavior есть `enc.name == "movie.obu"`, но в interfaces `StreamInfo` поле `name` есть, а в `check_pair` оно не упомянуто. Убедиться, что проверка по имени тоже реализована.

### Уровень риска: MEDIUM
Основной риск — тонкая логика `pick_points` и `point_verdict` с edge cases на симметричном контенте и нестандартных раскладках сцен. Покрытие тестами хорошее, но два дополнительных кейса (нечётные точки, симметричный контент) закрыли бы лазейки.

## 10-03-PLAN.md — I/O-слой frames.py

### Сильные стороны
- `-seek_timestamp 1` + абсолютный pts — критическая находка исследования (Pitfall 1) закреплена как обязательная; тесты на VFR и start_time≠0 покрывают.
- Кэш pts через JSON + `os.replace` + ключ `(path, size, mtime_ns)` — безопасная схема (не pickle, атомарная запись, валидация при чтении).
- `nice` префиксом argv, а не `preexec_fn` — правильный выбор для многопоточной программы (A1).
- Проверка `len(stdout) == count·W·H·3` — защита от молчаливого получения короткого/пустого вывода.

### Замечания
- **HIGH.** Парсинг DV side data (`dv_profile` из `stream_side_data`) — ASSUMED A6, имена полей ffprobe не сверены на реальном P5-файле. Plan это честно признаёт и откладывает проверку на UAT 10-05, но если поля иные — `probe_stream` вернёт `dv_profile=None` при `has_dovi=True`, и `precheck.check_pair` откажет пару с причиной «профиль Dolby Vision не определён». Это **ложный отказ** для корректного DV-файла, который не будет обнаружен до UAT. Рекомендую: в Task 1 добавить fp-тест с **двумя** вариантами JSON side_data — одним гипотетическим (по предположению) и одним альтернативным (например, `dv_profile` вложенный в `tags` или `dv_config`), чтобы при несовпадении с реальностью исполнитель сразу увидел, какой формат ожидать. Или: в `probe_stream` сделать разбор максимально терпимым (искать `dv_profile` рекурсивно во всех вложенных dict/list side_data).
- **MEDIUM.** `pts_table` читает `packet=pts_time` через `-of csv=p=0`. На файлах с несколькими видеотреками (редко, но бывает) `-select_streams v:0` выберет первый; если у оператора файл с `v:0` = основной поток и `v:1` = бонусный — это корректно. Но если `v:0` — не тот поток, который энкодил enpipe, таблица pts будет не та. Plan не проверяет, что `v:0` — тот же поток, что в `probe_stream`. Рекомендую: в `pts_table` принимать опциональный `stream_index: int = 0` и в `check_pair_files` (10-04) передавать индекс, полученный из `probe_stream` (или хотя бы записать в комментарий, что `v:0` — контракт).
- **MEDIUM.** Кэш pts: `mtime_ns` на ZFS может не обновляться при копировании файла (cp --preserve). Если оператор скопирует файл на NAS и обратно, mtime_ns может остаться старым, а содержимое — другим. Кэш вернёт старую таблицу. Размер файла (в ключе) спасёт, если размер изменился; но если два разных файла одного размера (например, обрезка с тем же числом кадров) — не спасёт. Это крайне маловероятно (нужны два файла одинакового размера с разными pts), но стоит упомянуть в docstring кэша как известное ограничение.
- **LOW.** `grab_frames` проверяет нечётные width/height **до** запуска процесса. Но `probe_stream` уже вернул эти значения — почему бы не проверить их в `probe_stream` или в `check_pair`? Двойная проверка не вредна, но создаёт три места, где можно забыть обновить контракт. Рекомендую комментарий в `grab_frames`: «дублирует проверку D-04 из precheck; защита от прямого вызова grab минутом предпроверки».

### Уровень риска: MEDIUM-HIGH
Риск в основном из-за DV side data (A6) — единственная непроверенная часть, которая может дать ложные отказы на реальном материале. Остальное хорошо покрыто.

## 10-04-PLAN.md — Оркестратор и медиа-тест

### Сильные стороны
- `test_shift_fixture_margin` — **отличная** защита от ослабления порога ради зелёных тестов (T-10-20). Запасная фикстура (шум + crf 20) вместо снижения `align_margin_db` — правильный инженерный выбор.
- `refused_report` как модельная функция (не CLI) — D-20 реализован полно: отказ выражается данными, рендер отделён.
- `grab_frame_pair` с локальным вердиктом D-14 — мост к фазе 11 готов.
- Worker-контракт `(result, err)` без `die()`/исключений — единообразие с `encoding/audio.py`.

### Замечания
- **MEDIUM.** `check_pair_files` при ошибке probe/pts на одном файле возвращает `PairCheck` с причиной, но **без** `src_info`/`enc_info`/`src_pts`/`enc_pts`. Если probe источника упал, а энкод прошёл — `src_info = None`, `enc_info` заполнен. В `grab_frame_pair` проверка `check.src_info is None` → «пара не прошла проверку». Но в `meta_with_check` при `src_info is None` поля `width`/`height`/`fps` не обновляются — это корректно (D-20: отказ без метрик), но если `meta` уже содержал width/height из другого источника (например, из CLI), они останутся. Это может ввести в заблуждение при рендере отчёта-отказа. Рекомендую: в `refused_report` явно обнулять width/height/fps при `src_info is None`, или добавить комментарий, что они берутся из meta, а не из check.
- **MEDIUM.** Медиа-тест (Task 3): генерация фикстур через `subprocess.run` в тесте — это нормально для integration-тира, но команды ffmpeg с `-x265-params colorprim=bt2020:transfer=smpte2084:colormatrix=bt2020nc:range=limited:log-level=error` могут сломаться при обновлении ffmpeg или x265. Plan не содержит `skipif` по успешности генерации фикстур — если `libx265` есть, но `x265-params` не принимает `colorprim` (маловероятно, но возможно в другой сборке), тест упадёт с непонятной ошибкой. Рекомендую: обернуть генерацию каждой фикстуры в `try/except subprocess.CalledProcessError` и `pytest.skip` с текстом «фикстура не сгенерирована: <причина>».
- **LOW.** `test_frame_pair_local_shift` (test 9) строит `PairCheck` вручную с `dataclasses.replace`. Это хрупко: если `PairCheck` изменится (например, добавится поле), тест сломается. Рекомендую: вынести хелпер `_build_check(...)` в фикстуру модуля, чтобы все тесты строили PairCheck одинаково.
- **LOW.** Время модуля ≤ 60 с — амбициозно для 10+ тестов с генерацией фикстур и реальным ffmpeg. Plan предусматривает сокращение (duration до 3 с, меньше N в framemd5), но не учитывает, что `test_shift_fixture_margin` может запустить **двойную** генерацию фикстур (основная + запасная). На 16 ядрах с ultrafast/preset 12 это, вероятно, укладывается, но на 4-ядерной машине оператора — может не уложиться. Это не провал (plan говорит «записать как отклонение»), но стоит снизить ожидание до 90 с для безопасности.

### Уровень риска: MEDIUM
План самый объёмный и содержит самый сложный тест (медиа-тест). Риск в хрупкости ffmpeg-команд и времени прогона. Защита порога через `test_shift_fixture_margin` — сильное место, компенсирующее риск.

Если скрипт работает на синтетике, но падает на 4K — оператор получит ошибку и не сможет проверить A8. Рекомендую: в Task 1 добавить `try/except` вокруг каждого шага с печатью трассировки, чтобы оператор мог прислать полный вывод, а не «упало на шаге 3».
- **MEDIUM.** Замер jobs со сдвигом точек на `index * 997 % len` — хорошая идея для обхода page cache, но 997 — простое число, и при `len(pts)` кратном 997 (крайне маловероятно, но) сдвиг даст 0. Рекомендую: использовать `index * 997 + 1` или просто `index * 1000` — проще и достаточно.
- **LOW.** Если A8 не подтверждён (теги энкода потеряны), план записывает блокер в STATE.md, но не определяет, **какие именно** теги потеряны. Рекомендую: в Task 3 добавить детализацию «какие теги расходятся» и разные действия для разных случаев.

### Agreed Concerns

Qwen: добор равномерных точек при несимметричных сценах и порядок сортировки/`isclose` при ничьей лучший-второй в `point_verdict` не формализованы — добавить тесты (3 точки, сцены (0,10),(10,20),(20,96); симметричный ±1).
2. **[MEDIUM] Риск ложных отказов на реальном контенте.** OpenCode: склейки без повторных точек — при ≥3 малоподвижных склейках файл получит «неопределённо» без попытки другой точки (зафиксировать как известное ограничение; место для ретрая оставить в `AlignTarget`). Qwen: A6 (имена полей DV side data) — если не совпадут, корректный DV P5 будет отвергнут; сделать разбор терпимым или заранее снять JSON `ffprobe` с реального P5 у оператора.
