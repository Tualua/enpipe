поэтому IN-08 повышен до WR-06. Ложного «выровнено» это не даёт, блокеров нет.
IN-02..IN-07 не исправлялись и перенесены как замечания. IN-06 после 10-09
проявляется ещё чаще. Новое замечание IN-09: разнос голосов неявно привязан к

## Предупреждения

### WR-06: после 10-09 повторы D-11 не выполняются ни на одном энкоде короче 226 кадров; принятое последствие описано с заниженным масштабом (было IN-08)

**Файл:** `src/enpipe/analysis/pair.py:155-175`, `src/enpipe/analysis/pair.py:205-207`, `src/enpipe/analysis/align.py:178`; документация последствия: `pair.py:163-165`, `10-09-SUMMARY.md` (decisions), `10-09-PLAN.md` T-10-09-04
**Проблема:** `_taken_frames` запрещает повторы в ±`vote_separation` (±24) от
каждой из 5 целей, а `_point_worker` такие повторы просто пропускает
(`continue`), не сдвигая их. Каждая окрестность закрывает 49 кадров. При шаге
целей `(n−1)/4` не больше ~56 окрестности покрывают почти весь файл. Повторы
идут через 48, поэтому каждый из них попадает в окрестность соседней цели.
Посчитано через `pick_points`, `retry_frames` и `_taken_frames` (n = длина
энкода, «доля» — средняя доля разрешённых повторов):

```
длины       до 10-09 (±6): все повторы отпали / доля   после 10-09 (±24): все отпали / доля
[26,200)    58 длин / 0.47                             151 длина (49..199, т.е. все) / 0.00
[200,400)    2 длины / 0.84                            28 длин (200..225, 241, 289) / 0.40
[400,800)    0 / 0.95                                  0 / 0.78
[800,2000)   0 / 1.00                                  0 / 1.00
```

На длинах 26..48 повторов нет вообще (первый повтор 48 уже за концом файла).
Получается, что D-11 выключен для любого энкода короче 226 кадров (≈ 9,4 с при
24 fps). Конкретные случаи:

```
n=150: повторы [48,96,144,85,133,123]; до 10-09 разрешено 5, теперь []
n=225: повторы [48,96,144,104,152,200,160,208,216]; до 10-09 разрешены все 9, теперь []
n=220, движение 45..51 и 93..99 (статика вокруг целей 0,55,110,164,219):
  ok=False undetermined n_aligned=0, кадры энкода [0,55,110,164,219] — ни одного повтора
```

Вердикт остаётся консервативным: ложного «выровнено» нет, будет только лишний
отказ «неопределённо». Но короткие клипы — это ровно то, на чём анализ
калибруют и прогоняют на пробах (медиа интеграционных тестов длиной 4 с,
96 кадров). На малоподвижных клипах до ~9 с проверка будет отказывать всегда,
если движение не совпадёт с одной из пяти целей. Главное: оператор принимал
последствие (T-10-09-04, комментарий в `_taken_frames`, SUMMARY) в формулировке
«на части длин (121, 165, 189)». Фактически это весь диапазон 49..225. Решение
принималось на неверных данных. Тест `test_static_121_retries_skipped`
закрепляет один случай и не показывает масштаб.

**Исправление:** это решение оператора, отдельная развилка, не нужно
связывать его с WR-05. Варианты:
1. Сдвигать повтор, а не пропускать его. Брать первый кадр за окрестностью и
   сохранять разнос > sep между повторами одной точки:
   ```python
   f = target.enc_frame
   for _ in range(cfg.align_retry_max):
       f += cfg.align_retry_step
       while f in taken and f < n_enc:
           f += 1
       if f >= n_enc:
           break
       again = _measure(...)
   ```
   Повторы разных точек при этом могут сойтись рядом. Подсчёт `aggregate` с
   тем же sep это закрывает.
2. Оставить как есть, но исправить формулировку в комментарии `_taken_frames`,
   в SUMMARY и T-10-09-04 («повторы D-11 не выполняются на энкодах короче
   ~226 кадров при дефолтах»). Добавить параметризованный тест на границы:
   n = 225 — ни одного повтора, n = 226 — повторы 144 и 200.

## Замечания

### IN-02: «сдвиг не менее W» теряется в итоге файла и в строках кадров (частично исправлено, без изменений)

**Файл:** `src/enpipe/analysis/model.py:241-248`, `src/enpipe/analysis/model.py:278-279`, `src/enpipe/analysis/report.py:297-302`, `src/enpipe/analysis/report.py:343`
**Проблема:** причина отказа печатает «≥» (`pair.py:312`), а
`_alignment_summary` выводит «итог: сдвиг +3». `_frame_cells` для кадра отчёта
(окно ±1, где любой сдвиг означает «не менее») выводит «сдвиг +1». В
report.json граница тоже теряется.
**Исправление:** добавить последним полем `shift_at_least: bool = False` в
`FileAlignment` (заполнять в `aggregate` из `shifted[0]`) и в `FrameRow`,
передавать его в `_alignment_text`. Golden обновлять осознанно.

### IN-03: `offset_hints` пропускает диапазон после сцены нулевой длины (без изменений)

**Файл:** `src/enpipe/analysis/precheck.py:102-110`
**Проблема:** окно с `lens[lo] == 0` отбрасывается целиком, хотя окно
`[lo+1, hi]` с той же суммой подходит. `[(0,0),(0,5)]` и `[(0,3),(3,3),(3,8)]`
при `n_enc = 5` дают пустые подсказки. Теряется только подсказка в тексте
отказа.
**Исправление:** пропускать ведущие сцены нулевой длины
(`while lo < hi and lens[lo] == 0: lo += 1`) перед проверкой
`lens[lo] > 0 and lens[hi] > 0`; добавить оба случая в `test_precheck.py`.

### IN-04: `UnicodeDecodeError` выходит из `check_pair_files` (без изменений)

**Файл:** `src/enpipe/analysis/frames.py:100`, `src/enpipe/analysis/pair.py:268-273`
**Проблема:** ffprobe запускается с `text=True` без `errors=`. Байты не в UTF-8
в сообщениях `-v error` вызывают `UnicodeDecodeError`. Цикл probe ловит только
`AnalysisError`, поэтому исключение уходит к вызывающему.
**Исправление:** `errors="replace"` в `_proc.run` либо байтовый режим с
декодированием через `"replace"`.

### IN-05: нет таймаута у ffmpeg/ffprobe (без изменений)

**Файл:** `src/enpipe/analysis/frames.py:100`
**Проблема:** повисший ffmpeg (битый файл, зависшее чтение с NAS) навсегда
блокирует поток пула.
**Исправление:** передавать `timeout=`, а `subprocess.TimeoutExpired`
превращать в `AnalysisError`.

### IN-06: итог «выровнено N из M» расходится с таблицей точек (без изменений, после 10-09 проявляется ещё чаще)

**Файл:** `src/enpipe/analysis/align.py:195-205`, `src/enpipe/analysis/report.py:302`, `src/enpipe/analysis/report.py:305-325`, `src/enpipe/analysis/pair.py:317-321`
**Проблема:** `points` сохраняет соседей, а `n_aligned` считает только голоса
с разносом > 24 кадров. На коротких энкодах (шаг целей ≤ 24, n ≤ ~97) соседние
цели систематически не засчитываются. Пример из `test_point_error_reason`: в
таблице «выровнено» у 0, 24, 71 и 95, а в причине «выровнено 2 из 5». Вердикт
верен, но по отчёту не видно, какие строки не засчитаны.
**Исправление:** возвращать из `aggregate` засчитанные кадры (последнее поле
`counted: Tuple[int, ...]` в `FileAlignment`) и помечать остальные строки как
«не засчитано: ближе 24 кадров к N». Golden обновлять осознанно.

### IN-07: замер jobs в scratch-скрипте обрывается на первой ошибке точки (без изменений)

**Файл:** `scratch/analysis_pair_probe.py:169-192`
**Проблема:** `pool.map(_grab_point, ...)` пробрасывает первое
`AnalysisError`, и весь шаг 5 падает без замеров. При `len(sp) < 7` окно
`_WINDOW` оказывается больше файла. На выход enpipe это не влияет.
**Исправление:** ловить `AnalysisError` в `_grab_point`; брать окно
`min(_WINDOW, len(sp))`.

### IN-09: критерий независимости голосов неявно зависит от шага повтора (новое, 10-09)

**Файл:** `src/enpipe/analysis/align.py:166-178`, `src/enpipe/analysis/config.py:126-132`
**Проблема:** `vote_separation = max(2W, align_retry_step // 2)`. Порог
«разные места файла» (D-13) выводится из параметра, который по смыслу задаёт
только шаг поиска движения (D-11). Если при калибровке поднять
`align_retry_step`, например до 240 (10 с), чтобы искать движение дальше,
незаметно вырастут и разнос голосов (120), и окрестность запрета повторов
(±120). Максимум голосов на энкоде станет `⌊(n−1)/120⌋ + 1`, и WR-06
распространится на файлы примерно до 1000 кадров. Оба значения provisional и
попадают в отчёт как пороги, но связь между ними видна только в docstring.
**Исправление:** вынести разнос в отдельное provisional-поле
`AnalyzeConfig.align_vote_sep: int = 24` с проверкой
`2·align_window ≤ align_vote_sep < align_retry_step` в `__post_init__` и
брать его в `vote_separation`. Тогда порог виден в report.json отдельной
строкой. Golden нужно обновить осознанно (добавится порог).
