# Обзор планов Фазы 8: Усиление замка COR-02

## 1. Сводная оценка

Фаза 8 — хорошо структурированная, последовательно спланированная серия из 5 планов, закрывающая критические пробелы верификации фазы 7 (WR-01..03). Архитектурное решение о побайтном гейте (D-01) вместо PSNR-порога — **фундаментально правильное**: оно устраняет главный класс ложноположительных срабатываний. Введение третьей категории исхода `METRICS_FAILED` (D-12) — зрелое инженерное решение, позволяющее покрыть путь с метриками без блокировки всей фазы на нестабильном внешнем компоненте. Зависимости между волнами (wave 1→2→3→4) логичны, TDD-подход в планах 02/03/04 корректен.

---

## 2. Сильные стороны

- **D-02 как стоп-гейт перед переписыванием харнесса** (08-01): проверка допущения «qsvencc детерминирован» на железе до любых правок кода — правильный порядок действий; экономит время при отрицательном результате
- **Побайтный гейт + диагностика раздельно** (D-01): `same_bytes()` дёшев, `sweep_chunk()` запускается только при расхождении — оптимально по времени для ~640 сессий матрицы
- **`METRICS_FAILED` как третья категория** (D-12): не маскирует порчу под отказ метрик (T-08-07) и не блокирует замок на известном дефекте внешнего компонента; отсутствие порога допустимой доли — консервативно и правильно
- **`same_bytes()` перед `verify_frames()`** (08-03 Task 1): для побайтно отличных сессий ошибки сверки кадров уходят в `diag`, а не пробрасываются `HarnessError` — это предотвращает маскировку порчи под harness_error (T-08-07b)
- **Ретраи эталона `metrics=True` до 5 попыток** (D-13): учитывает измеренную нестабильность (1/9 отказов в изоляции)
- **Четвёртая нога триады проверяет наличие строк и `Frames:`, но не значения PSNR/SSIM** (D-09): соответствует установленному факту недостоверности значений метрик (33.9 vs 48.2 дБ на идентичном выходе)
- **Страж Dockerfile в fast-tier** (08-02 Task 1): `test_runtime_dockerfile.py` предотвратит регрессию структуры образа без GPU
- **Человеческий чекпоинт D-07** (08-02 Task 3): единственный способ проверить GPU в рантайм-образе (docker недоступен в девконтейнере); учёт D-14 (до 3 повторов) в инструкциях

## 3. Проблемы и риски

### HIGH severity

- **[08-03] `verify_frames` бросает `HarnessError` для побайтно идентичных сессий, но `run_concurrent` не ловит его явно для ветки `identical=True`**
  
  В плане указано: *«Ветка `identical`: `verify_frames(...)` — HarnessError пробрасывается наружу»*. Это означает, что **любая** проблема со сверкой кадров на идентичной сессии (например, `ffprobe -count_frames` вернёт неожиданное число из-за бага парсера OBU) **убьёт всю матрицу/замок**, даже если побайтное сравнение уже доказало корректность. Риск: ложный `HarnessError` из `verify_frames` (не связанный с COR-02) заблокирует прохождение D-10b.
  
  **Рекомендация:** рассмотреть `try/except HarnessError` в ветке `identical` с записью в diag и статусом `byte_identical=True, frames_bad=True`, а не пробросом. Текущее поведение («пробрасывать») должно быть явным решением с комментарием WHY.

- **[08-05 Task 1] D-10c (непустота на r4604) выполняется ПЕРЕД D-10a/D-10b, но зависит от скачивания и распаковки стороннего .deb**
  
  Если SHA256 r4604 (.deb 8.31 release) изменится или URL станет недоступным — весь план 08-05 остановится. План фиксирует `15aa733f...`, но GitHub Releases .deb permalink может сломаться.
  
  **Рекомендация:** добавить в acceptance criteria проверку sha256 скачанного файла; при неудаче скачать предложить пользователю вручную альтернативу.

### MEDIUM severity

- **[08-01] Пробник `probe_d02_byte_identity.py` — одноразовый скрипт в scratch/, не покрытый тестами**
  
  План требует создать сложный скрипт (~300 строк) с конкурентными запусками qsvencc, но не предусматривает для него unit-тестов. Ошибки в классификации сессий (METRICS_FAILED vs SESSION_FAILED) в самом пробнике могут дать ложный D-02 PASS/FAIL.
  
  **Рекомендация:** добавить в verify хотя бы `py_compile` и `--help` (есть), плюс grep-проверку ключевых строк (`VIDEOMETRIC`, `D-02 PASS`, `sha256`). Уже есть в AC — хорошо.

- **[08-03] `SessionOutcome` расширяется новыми полями со значениями по умолчанию `None`/`()`
  
  Все существующие потребители `SessionOutcome` (если есть вне харнесса) получат `byte_identical=None`, `diag=None`, `triad_missing=()`. Код, проверяющий `outcome.corrupt_frames or 0`, продолжит работать, но код, читающий `.status` и ожидающий только `SESSION_OK/SESSION_FAILED/SWEEP_SKIPPED`, не узнает `METRICS_FAILED`.
  
  **Проверка:** `grep -r "SessionOutcome" --include="*.py"` вне `_concurrency_harness.py` — только `test_concurrency_immunity.py` и `gate_stress_matrix.py`, оба обновляются в 08-04. Риск низкий, но стоит явно проверить.

- **[08-04 Task 3] `_run_cli_metrics_retry` повторяет при `is_metrics_failure(str(exc))`, но `die()` обрезает stderr до 500 символов**
  
  В `enpipe/shared/logging.py` сообщение `die()` содержит `(хвост stderr 500)` — маркеры `VIDEOMETRIC:` / `allocVA` могут оказаться за пределами 500 символов (особенно при длинных argv qsvencc). Это приведёт к тому, что `is_metrics_failure` не распознает отказ метрик и повтор не произойдёт.
  
  **Рекомендация:** либо расширить контекст проверки (читать полный лог сессии, а не только сообщение exc), либо задокументировать это ограничение в плане как известный риск.

- **[08-02] Перенос рантайм-образа на ubuntu:24.04 — breaking change для пользователей образа**
  
  Текущие пользователи GHCR-образа на trixie получат неработоспособный апгрейд. План не предусматривает механизма миграции (отдельный тег? deprecation notice?).
  
  **Рекомендация:** добавить в docker/README.md раздел «Migration from trixie image» с ключевыми различиями.

### LOW severity

- **[08-03] Регэксп `_METRICS_FRAMES_RE` для извлечения `Frames:` из строк метрик**
  
  Формат подтверждён на железе для r4634, но qsvencc может изменить формат строки в следующих версиях. План правильно выбирает локальный регэксп в харнессе (не меняя `src/enpipe/encoding/chunk.py::parse_metrics`).
  
  **Статус:** принято, риск минимален.

- **[08-05] Матрица ~640 сессий — время выполнения ~1 час**
  
  План упоминает запуск в фоне (`run_in_background`), но 10-минутный лимит foreground-вызова инструмента может быть недостаточен для ожидания завершения. Нужно убедиться, что инструмент поддерживает фоновый режим.
  
  **Статус:** документировано, решение за исполнителем.

- **[08-04 Task 2] Стресс-матрица удаляет ref_workdir только в `finally` всего прогона**
  
  При аварийном прерывании (SIGKILL/OOM) каталог эталонов не удалится. Это не проблема корректности (остаточные файлы в scratch/), но засоряет диск при repeated runs.
  
  **Статус:** приемлемо для scratch/-скрипта.

## 08-01-PLAN.md — Стоп-гейт побайтного детерминизма

### Сильные стороны
- **Правильный порядок:** проверка предпосылки (D-02) до任何 кодовых изменений — если детерминизма нет, фаза останавливается без мусора в дереве.
- **Минимальный blast radius:** одноразовый скрипт в `scratch/`, харнесс фазы 7 не тронут, `.gitignore` обновлён.
- **Два эталона (ref_a / ref_b):** проверяет изолированный детерминизм, а не только «конкурентная == изолированная».
- **Классификация METRICS_FAILED заранее:** корректно учитывает нестабильность метрик (D-12) ещё до основного харнесса.

### Замечания
- **[MEDIUM] Хрупкий sys.path shim.** Пробник импортирует `_concurrency_harness` через `sys.path.insert`. Это работает, но если харнесс фазы 7 когда-нибудь переместится или переименуется, пробник сломается молча. Рекомендация: добавить `try/except ImportError` с понятным сообщением.
- **[LOW] `--iters 3` по умолчанию.** Для стоп-гейта на 3 сценах × 2 варианта × 3 итерации = 18 сессий + 6 эталонов. Достаточно для предварительного вывода, но research-замер (15+9) был примерно того же объёма. Стоит ли увеличивать до 5 — на усмотрение исполнителя.
- **[LOW] sha256 vs filecmp.** План выбирает sha256 (правильно, т.к. дайджест идёт в лог), но для файлов .obu размером в сотни МБ `read_bytes()` на каждом эталоне читает всё в память. Для 3 сцен × 2 эталона + 18 сессий это приемлемо, но стоит отметить в docstring пробника.

### Риск: LOW

## 08-02-PLAN.md — Рантайм-образ на Ubuntu 24.04

### Сильные стороны
- **Pitfall 4 (venv) учтён:** builder-стадия тоже на `ubuntu:24.04` с `UV_PYTHON=/usr/bin/python3.12` — это ключевой момент, который легко пропустить.
- **Fast-tier страж `test_runtime_dockerfile.py`:** структурные свойства Dockerfile проверяются автоматически и навсегда.
- **Блок qsvencc переносится дословно:** `test_qsvencc_threshold_sync.py` не ломается — критичный страж синхронности пинов.
- **Human checkpoint с готовыми командами:** D-07/D-14 оформлены как copy-paste-ready инструкции с учётом нестабильности метрик (до 3 повторов).

### Замечания
- **[HIGH] Путь `libigdrcl.so` — предположение A3.** RESEARCH явно помечает это как ASSUMED. План записывает `test -e /usr/lib/x86_64-linux-gnu/intel-opencl/libigdrcl.so` как acceptance criterion, но если путь другой (например, `libigdrcl.so.1` или подкаталог другой), сборка упадёт, и исполнитель в девконтейнере не сможет это проверить (нет docker). Рекомендация: в Task 1 добавить `RUN dpkg -L intel-opencl-icd | grep -q '\.so'` как более устойчивую проверку, или выполнить `dpkg -L intel-opencl-icd` в девконтейнере *до* написания Dockerfile и зафиксировать точный путь.
- **[MEDIUM] Wave 1 с блокирующим human checkpoint.** 08-02 в wave 1 (параллельно с 08-01), но Task 3 — blocking human checkpoint. Если пользователь недоступен день, wave 2 (08-03) не стартует. Фактически 08-03 не зависит от 08-02 (харнесс не нуждается в новом образе), поэтому `depends_on: []` корректно. Но стоит явно зафиксировать, что 08-03 может стартовать немедленно, не дожидаясь human checkpoint.
- **[MEDIUM] `software-properties-common` + `add-apt-repository`.** PPA-подключение через `add-apt-repository` в Docker-сборке на CI-раннере: этот пакет тянет довольно много зависимостей. Альтернатива — прямая запись `.sources`-файла (как в девконтейнере: `/etc/apt/sources.list.d/kobuk-team-ubuntu-intel-graphics-noble.sources`). Это быстрее и воспроизводимее. План упоминает deb822-формат в контексте удаления `sed`, но не рассматривает прямую запись для PPA.
- **[LOW] `gpg-agent` в apt-install.** Указан в списке пакетов, но не очевидно, зачем. Вероятно, для `add-apt-repository` (подпись ключа). Стоит WHY-комментарий.

### Риск: MEDIUM (из-за непроверяемого предположения A3 и невозможности локальной верификации)

## 08-03-PLAN.md — Переписывание харнесса (ядро фазы)

### Сильные стороны
- **Классификация `byte_mismatch` vs `HarnessError`:** побайтно отличная сессия *никогда* не бросает HarnessError — это критически важно для D-10c (r4604 может ломать и число кадров, и PSNR-свип).
- **Порядок `same_bytes` → `verify_frames`:** гейт вычисляется первым, до любых проверок, которые могут бросить. Это предотвращает маскировку порчи под harness_error.
- **Три отдельных исхода:** SESSION_OK / SESSION_FAILED / METRICS_FAILED — чёткая таксономия без сворачивания.
- **Ретраи эталона (D-13):** до 5 попыток для metrics=True с проверкой rc и числа кадров.
- **Fast-tier тесты без GPU:** `test_harness_gates.py` покрывает всю логику monkeypatch'ами.

### Замечания
- **[HIGH] Объём одного плана.** Task 1 добавляет: `sha256_file`, `same_bytes`, `decoded_frames`, `verify_frames`, `METRICS_FAILED`, `is_metrics_failure`, `reference_paths`, `REF_MAX_ATTEMPTS_METRICS`, переписывает `build_isolated_reference` (ретраи), `run_concurrent` (полная переклассификация), `sweep_chunk` (-xerror + сверка строк), `qsvencc_command` (metrics-параметр), `_build_command`, `_session_worker`, `triad_for`, `reference_triad_violations`. Это ~15 изменений в одном файле за один план. Если одно из них сломает существующий тест — откат всего Task 1. Рекомендация: рассмотреть разбивку на 08-03a (byte gate + frame count + METRICS_FAILED, без triad) и 08-03b (4-я нога triad + reference retries).
- **[MEDIUM] `verify_frames` для побайтно идентичных сессий бросает HarnessError.** Это правильно (баг эталона/харнесса), но создаёт сценарий: эталон построен с `metrics=True` после 5 ретраев, `count_frames == scene.frames` проверен. Затем конкурентная сессия побайтно совпала, но `decoded_frames` возвращает другое число (например, из-за race condition в ffprobe). HarnessError прерывает весь прогон. Стоит добавить в docstring `run_concurrent`, что это *намеренное* поведение: идентичный байтам выход с неверным числом кадров = фундаментальная проблема, которую нельзя замолчать.
- **[MEDIUM] `sweep_chunk` с `-xerror` + сверка строк PSNR.** RESEARCH показал, что `-xerror` на ffmpeg 6.1.1 не даёт ненулевой rc на битых пакетах. План добавляет сверку строк stats-файла с `ref_count`, но это *после* прогона ffmpeg. Если ffmpeg упал с rc≠0 (усечённый файл), `HarnessError` от `proc.returncode != 0` всё ещё срабатывает. Но если rc=0 при битых данных — строки PSNR могут быть неполными. План это покрывает (сверка `lines != ref_count`), но порядок: сначала rc, потом строки — стоит зафиксировать явно.
- **[LOW] Язык файлов.** План фиксирует отступление (английский в `tests/integration/*`) — это правильно и прозрачно.

### Риск: MEDIUM-HIGH (объём изменений + непроверяемость всех кейсов без GPU)

## 08-04-PLAN.md — Подключение потребителей

### Сильные стороны

### Замечания
- **[MEDIUM] `test_sdr_legacy_oracle_parity` с метриками.** План параметризует этот тест: при `metrics=True` обе стороны (legacy и enpipe) идут с метриками, с ретраями на VIDEOMETRIC. Но: legacy-сторона — это subprocess `legacy/encode_scenes.py`, который *заморожен*. Если legacy-сторона падает по VIDEOMETRIC 3 раза, а enpipe проходит — тест падает. План говорит «legacy-subprocess повторять до 3 раз», но не описывает, что делать, если legacy стабильно падает, а enpipe нет. Это может сделать `[metrics]`-вариант постоянно красным. Рекомендация: добавить условие «если legacy упал 3× по метрикам, а enpipe прошёл — записать как METRICS_FAILED (legacy), не как FAIL».
- **[MEDIUM] Стресс-матрица: ~640 сессий × 2 варианта × декод-сверка.** Каждая сессия теперь включает `ffprobe -count_frames` (дополнительный subprocess). При 640+ сессиях это добавляет заметное время. План упоминает «время ×2», но не даёт оценку абсолютного wall time. Если фаза 7 дала 320 сессий за ~20 мин, то фаза 8: 640 сессий × 2 (декод-сверка) + эталоны × 2 = ~60-80 мин. Это важно для планирования background-запуска.
- **[LOW] `gate_stress_matrix.py` HarnessError из `run_concurrent`.** План добавляет `try/except harness.HarnessError` в матрице, считая `harness_errors += 1`. Но HarnessError из `run_concurrent` теперь возможен только для побайтно идентичных сессий (08-03). Если он случится — это баг эталона, и продолжение прогона может дать ложные «чисто» для оставшихся итераций. Стоит рассмотреть: при HarnessError из `run_concurrent` прерывать весь прогон, а не считать инкрементом.
- **[LOW] `scratch/parity_encode.py` `PARITY_METRICS=1` по умолчанию.** Если метрики нестабильны (6/15 отказов при JOBS=3), паритет по умолчанию будет падать ~40% случаев. Ретраи (3×) снизят, но не устранят. Исполнитель должен быть готов к повторным запускам.

### Замечания
- **[HIGH] D-10c: побайтный критерий на r4604 может не воспроизвести порчу.** RESEARCH измерял порчу на r4604 по PSNR-свипу (фазы 6-7). Побайтный критерий — новый. Если r4604 даёт *побайтно идентичный* выход в изоляции, но *побайтно различный* в конкуренции — всё ОК. Но если r4604 *всегда* побайтно идентичен (т.к. портит кадры внутри того же argv, а не между argv) — побайтный критерий не воспроизведёт порчу, и фаза остановится. Это фундаментальный риск: смена критерия может сделать замок вакуумным на старом бинаре. Рекомендация: в Task 1 явно описать fallback — если побайтный критерий дал 0 расхождений на r4604, но PSNR-свип дал >0 corrupt, это *не* СТОП, а информация: побайтный критерий строгости достаточен, чтобы r4604 не портит байты (коррупция — внутрикадровая, не межфайловая). Тогда D-10c считается пройденным по PSNR-свипу (как в фазе 7), а не по байтам.

План говорит «в фоне», но не описывает механизм ожидания: `run_in_background` + `list_agents` + `send_message`? Или просто background-agent с `run_in_background: true`? Стоит явно прописать.
- **[MEDIUM] D-10d: `test_hardware_real_media.py` с метриками.** Если `[metrics]`-вариант test_sdr падает 3 раза подряд по VIDEOMETRIC — это 3 потерянных минуты. При 3 параметризованных тестах × 3 повтора × ~1 мин = до 27 мин на ретраи. План не учитывает это в оценке времени.

## Consensus Summary

Оба ревьюера оценивают общий риск как **MEDIUM**. Фундаментальных переделок никто не требует. Побайтный гейт (D-01), стоп-гейт D-02 до переписывания харнесса и отдельный исход `METRICS_FAILED` (D-12) оба признают правильными решениями.

### Agreed Strengths
- D-02 выполняется первым и останавливает фазу до любых правок кода (08-01).
- `same_bytes` вычисляется раньше `verify_frames`: расходящаяся сессия никогда не превращается в `HarnessError` (08-03, T-08-07b).
- `METRICS_FAILED` — третья категория без порога доли. Порчу она не маскирует и замок на дефекте внешнего компонента не блокирует.
- Четвёртая нога триады проверяет наличие строк метрик и `Frames:`, но не значения (значения недостоверны).
- Ретраи эталона metrics=True до 5 попыток (D-13). Fast-tier страж Dockerfile.

### Agreed Concerns (приоритет)
1. **`HarnessError` в ветке `identical` у `run_concurrent` (08-03).** OpenCode: HIGH, Qwen: MEDIUM. Побайтно совпавшая сессия с неверным `decoded_frames`, например из-за сбоя ffprobe, роняет весь прогон замка или матрицы. Оба просят зафиксировать это как *намеренное* поведение: комментарий WHY в docstring плюс fast-tier тест (тест уже есть в 08-03). OpenCode дополнительно предлагает альтернативу: писать в `diag` с флагом `frames_bad`, не пробрасывать. Qwen (08-04) предлагает обратное для матрицы: при `HarnessError` прерывать весь прогон, а не считать инкрементом.
2. **Длительность аппаратных прогонов (08-04/08-05).** Матрица около 640 сессий плюс `ffprobe -count_frames` на каждую — это примерно 60–80 мин. Ретраи D-10d могут добавить до ~27 мин. Нужен явный фоновый запуск.
3. **Ретраи метрик в аппаратном тире (08-04 Task 3).** OpenCode (MEDIUM): `die()` обрезает stderr до 500 символов, маркер VIDEOMETRIC может не попасть, и тогда повтора не будет. Qwen (MEDIUM): legacy-сторона паритета заморожена, и при стабильном отказе метрик у legacy `[metrics]`-вариант будет вечно красным. Оба пункта касаются надёжности D-10d при нестабильных метриках.

### Divergent Views
- **Объём 08-03.** Qwen (HIGH) предлагает разбить его на 08-03a (байтовый гейт + кадры + METRICS_FAILED) и 08-03b (триада + ретраи эталона). OpenCode объём не критикует. Ранее плановый чекер дал по этому поводу только info.
- **D-10c fallback.** Qwen (HIGH) предлагает засчитывать D-10c по PSNR-свипу, если побайтный критерий на r4604 даст 0 расхождений. **Это противоречит залоченному решению D-10c** («не даёт — стоп и доклад»). Само рассуждение тоже сомнительно: любая порча, которую видит PSNR-свип относительно изолированного эталона того же argv, обязательно меняет байты. Значит, «PSNR > 0, байты равны» невозможно. Рекомендация: не принимать.
- **Путь `libigdrcl.so` (A3).** Qwen оценивает как HIGH, но планировщик уже проверил путь через `dpkg -L intel-opencl-icd` в девконтейнере, и он подтверждён. Замечание неактуально.
