## ПОВОРОТ 2026-07-22: дефект qsvencc-СПЕЦИФИЧЕН, НЕ общий QSV-стек

Контр-эксперимент (ffmpeg `av1_qsv`, тот же oneVPL/libvpl рантайм, тот же Arc):
**0 битых кадров из 60 конкурентных итераций** (3-way, 5-way, sustained load),
включая точный хотспот (сцена 923 off299 / кадр 110079) — всегда inf PSNR,
бит-идентично. qsvencc при 3-way даёт ~35%. → Дефект НЕ универсальное свойство
конкурентного AV1-QSV на этом GPU; его провоцирует ЧТО-ТО, что делает qsvencc и НЕ
делает ffmpeg av1_qsv. Это ПЕРЕСМАТРИВАЕТ вывод «общий стек» (тот держался только на
старом громком #1626). Хорошая новость: вероятно чинится флагом qsvencc С СОХРАНЕНИЕМ
параллелизма.

Точная команда enpipe (`chunk.py::chunk_command`) отличается от чистого ffmpeg-теста:
- `--async-depth` auto=3 — НО ffmpeg-тест шёл на async_depth=4 (ВЫШЕ) и был чист →
  сама по себе async-depth вряд ли триггер.
- **`--b-pyramid --gop-ref-dist 6`** — тяжёлая B-пирамида (ffmpeg-тест b_strategy=-1,

  под конкуренцией → aliasing/подмена чужой поверхности.
- **`--output-depth 10`** (P010) vs 8-bit у ffmpeg-теста — второй кандидат.
- `--avhw --va` decode, `--scenario-info archive`, `--tune perceptual` — прочие отличия.

next_action: bisect qsvencc-флагов под 3-way конкуренцией (сцены 923/1129/928,
проверка off299), по одному knob'у: (1) убрать --b-pyramid / --gop-ref-dist 1,

## ИСХОДНЫЙ КОРЕНЬ (клон rigaya/QSVEnc, 2 агента, source-confirmed)

Баг найден в коде qsvencc: `QSVPipeline/qsv_allocator_va.cpp::AllocImpl` — цепочка
`else if` (~строки 326-341) маппит NV12→`VA_RT_FORMAT_YUV420` и т.д., но НЕТ ветки для
P010 → 10-bit поверхности создаются `vaCreateSurfaces(format = VA_FOURCC_P010)` —
МАЛФОРМИРОВАННЫЙ rt_format (должен быть `VA_RT_FORMAT_YUV420_10`). ffmpeg маппит верно.
Плюс `--output-depth 10` вставляет ДОП. MFX-VPP P010-пул (8→10 CSC), а `--gop-ref-dist 6`
+ b-pyramid держат ~6 таких поверхностей in-flight через async reorder-окно без host-sync
→ окно, в котором latent iHD/i915 cross-process GEM-buffer-reuse баг подменяет кадр.
Подтверждено двумя агентами (allocator + pipeline). Исключено в исходнике: DRM-prime
export (мёртв, DONOT_EXPORT), OpenCL-VA interop (мёртв, нет ICD), shared/global state (нет).
`--async-depth 1` не чинит (трогает только +AsyncDepth-член пула, не DPB-P010-пул → 7/15).

ПРАВИЛЬНЫЙ ФИКС (upstream/rebuild): добавить `else if (va_fourcc == VA_FOURCC_P010) {
format = VA_RT_FORMAT_YUV420_10; }` в AllocImpl. Сохраняет HW-decode+10-bit+B-frames+
zero-copy+полную скорость. Требует пересборки qsvencc; кандидат в PR rigaya/QSVEnc.
НЕ ВЕРИФИЦИРОВАН до сборки.

CLI-обходы ИСЧЕРПАНЫ: `--disable-va` СЕГФОЛТИТ 100% на этом Linux/iHD (и роняет в SW-decode
до краха); нет VA-memory-preserving флага, убирающего P010-пул. Рабочий обход в enpipe =
`--avsw` (SW-decode + HW-encode): чисто (0/60), сохраняет 10-bit+B-pyramid+DV/HDR (−0.6%
размер), но CPU-bound (310→125 fps single, 3-way 1.8s→4.1s тут). V1 (без B-frames, +29%
размер) и V3 (8-bit, теряет HDR) — прочие обходы. JOBS=1 НЕ использовать.

## Eliminated

- **seek+trim арифметика (`compute_chunk_seek_trim`, `keyframes.py`)** — ОПРОВЕРГНУТА. Изолированный энкод сцены 923 той же командой seek=01:16:14.167/trim=0:339 бит-точен на off299 (41.5 dB vs источник). Арифметика K=последний kf≤S, trim=(S-K):(E-1-K) корректна для этого источника.
- **Декод H.264 с B-кадрами при seek на не-keyframe** — не применимо: kf_frame=S=109780 (trim_start=0), seek приземляется точно на keyframe. И даже при этом изолированный декод чист.
- **Дубль СОСЕДНЕГО кадра внутри чанка** — ОПРОВЕРГНУТ. Битый 110079 не совпадает ни с одним соседом ±5 (все 12–19 dB); содержимое — из совершенно другой сцены (чужая QSV-сессия).
- **ICQ 24 vs 23** — red herring, подтверждено (влияет на качество, не на подмену содержимого).

## Resolution

- **root_cause:** enpipe запускает `JOBS` (дефолт 3) конкурентных сессий `qsvencc` на едином Intel Arc QSV/VA-API устройстве (`pipeline.py:240` `ThreadPoolExecutor(max_workers=args.jobs)`). Под конкурентной аппаратной нагрузкой QSV/oneVPL/iHD-стек изредка отдаёт один декодированный/энкодированный кадр с содержимым чужой сессии. Число кадров сохраняется → `count_frames` и инвариант frame-count проходят, а содержимое кадра молча битое (главный риск проекта — silent output corruption). Воспроизводится ~35% под 3-way конкуренцией, 0% в изоляции.
- **fix:** НЕ ПРИМЕНЁН — требует решения пользователя (tradeoff корректность↔throughput). Варианты:
  1. **JOBS=1 (сериализация GPU-сессий)** — гарантированно устраняет гонку (изоляция = 0% дефектов), но убирает параллелизм энкода (throughput ×1/3). Минимальное изменение, максимальная корректность. Рекомендуется как немедленный correctness-first дефолт для этого железа.
  2. **Пер-кадровая контент-верификация склейки** (не только `count_frames`) + пересборка битых чанков сериализованно. Дороже (нужен референс-декод/метрика), но сохраняет параллелизм. Детект, а не предотвращение.
  3. **Драйвер/qsvencc-уровень**: исследовать, есть ли режим, исключающий межсессионную контаминацию (отдельные VA-display уже есть — процессы раздельны; значит контаминация на уровне GPU/драйвера, обойти труднее). Возможно обновление iHD/oneVPL/qsvencc.
- **reproducer (scratchpad):** 3-way параллельный qsvencc сцен 923/1129/928, извлечь off299 сцены 923, PSNR vs эталонный изолированный chunk_off299; <30 dB = битый (~35% итераций). Эталон = изолированный энкод той же команды.
- **регрессионный инвариант:** любой фикс НЕ должен ломать keyframe-alignment и frame-count проверки. Вариант 1 (JOBS=1) их не затрагивает.

## Внешнее исследование (deep-research, 2026-07-22)

Агентный поиск (99 агентов, 17 источников, 25 проверенных утверждений). Итог:

- **Точный симптом не задокументирован нигде** (QSVEnc issues, iHD Known-Issue List,
  vpl-gpu-rt/libvpl/media-driver changelog, Jellyfin HWA guide) — тихая одно-кадровая
  межсессионная подмена при верном frame-count. Отсутствие в трекерах ≠ отсутствие бага.
- **Один корроборирующий репорт:** [intel/media-driver #1626](https://github.com/intel/media-driver/issues/1626)
  «AV1 ENCODE QSV/ARC - 2 encodes at same time results in errors» — 2 конкурентных
  AV1-QSV-энкода на Arc портят выход, один энкод чист («using only one encode and the
  problem goes away»). ТОТ ЖЕ класс (конкурентная AV1-порча на Arc), но ГРОМКИЙ отказ
  (чёрный экран + явные ffmpeg-ошибки) на СТАРОМ стеке (media-driver 23.1.2, ~2023).
  Не доказано, что это тот же дефект, что наш тихий вариант.
- **Общая проблема QSV-стека, не qsvencc-специфична:** #1626 воспроизводится через
  ffmpeg `av1_qsv` (другой фронтенд, тот же libvpl/libmfx-over-iHD рантайм). Дефект в
  общем Intel-рантайме, не в приложении Rigaya.
- **`Media SDK API v2.16` = oneVPL GPU runtime** (libmfx-gen/vpl-gpu-rt), НЕ legacy
  MediaSDK (тот вообще не поддерживает Arc; API v2.x = oneVPL по определению).
- **MFE (Multi-Frame Encode) исключён:** удалён в API 2.0, требует явного MFXJoinSession,
  невозможен между отдельными процессами.
- **Фиксов в новых версиях НЕТ:** iHD после 25.2.3 (25.3.4…26.1.5) и vpl-gpu-rt до 26.1.5 —
  НОЛЬ записей про concurrent/multi-session/context-isolation/cross-session. AV1-encode
  фиксы все single-session (TU1 corruption, TU7 hang). Единственный косвенный сигнал:
  vpl-gpu-rt 26.1.5 поправил DECODER surface-count math («prevent surface starvation at
  async depth > 1») — decoder-scoped, не межсессионная изоляция.
- **Официальных обходов нет** кроме «одна сессия за раз чиста» (что мы уже подтвердили).
  Нет задокументированного i915/Xe-параметра, GuC/HuC-уровня или VA/GPU-context флага
  для per-context surface isolation на DG2 при конкурентном сабмите.

**Вывод для фикса:** исследование НЕ нашло исправленной версии драйвера/библиотеки →
«просто обновиться» НЕ валидный escape. Это ПОДТВЕРЖДАЕТ выбор JOBS=1 как correctness-first
дефолт (единственный эмпирически-чистый путь, корроборирован #1626). Открытый вопрос: тихий

выделить P010 VPP-output/reference пулу отдельный AllocId/пул (глубже, не верифицировано);
и/или upstream-фикс изоляции буферов в iHD/i915. НЕ однострочник.

ОТКРЫТЫЙ АРТЕФАКТ: ветка Tualua/QSVEnc@p010-fix с инертным патчем (можно удалить или
