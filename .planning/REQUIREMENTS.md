# Requirements: enpipe

**Defined:** 2026-10-05
**Core Value:** Produce a correct, bit-exact scene-aware AV1 re-encode (keyframe-aligned chunks, preserved HDR/DV metadata, verified frame counts) from a source video on Intel Arc hardware — correctness of the encoded output is non-negotiable.

**Milestone scope (v1.3 Анализ качества энкода):** офлайн-подкоманда `enpipe analyze`, которая находит и показывает проблемные места готового энкода — включая потерю цвета мелких деталей, которую VMAF не видит. Путь кодирования (`encoding/`, `detection/`, `mkv/`) не меняется; новых runtime-зависимостей нет (ffmpeg n9.0.2 + numpy + stdlib). Основа: прототип `vmaf_frames.py` (2026-10-05), исследование `.planning/research/SUMMARY.md`, handoff `.planning/debug/HANDOFF-qsvencc-av1-small-chroma-loss.md`.

## v1.3 Requirements

### Вход и CLI (ANL)

- [ ] **ANL-01**: Пользователь запускает `enpipe analyze <src> <enc>` и получает отчёт по паре «источник — энкод» в папке `--out`.
- [ ] **ANL-02**: Пользователь передаёт папку вместо файла: пары находятся по `<stem>.Encoded.*`; источники без энкода и неоднозначные пары перечислены в сводке, код выхода ненулевой.
- [ ] **ANL-03**: `enpipe analyze` не требует GPU (программный декод по умолчанию) и может работать параллельно с идущим кодированием.
- [ ] **ANL-04**: В отчёте записаны метаданные запуска: версии ffmpeg/qsvencc (если известны), пороги, источники кандидатов — прогон воспроизводим.

### Выравнивание и извлечение (ALN)

- [ ] **ALN-01**: Кадр N извлекается точно по номеру (таблица pts + seek на полкадра раньше) из источника и энкода как 10-битный YUV без потерь.
- [ ] **ALN-02**: До расчёта метрик пара проверяется: размер, частота кадров, число кадров, теги диапазона/матрицы/transfer; не-PQ источник или несовпадение — громкий отказ с объяснением.
- [ ] **ALN-03**: Выравнивание проверяется в нескольких точках (включая склейки сцен) с тремя исходами — «выровнено / сдвиг N / неопределённо (статика)»; при сдвиге метрики не строятся, отказ.
- [ ] **ALN-04**: Для энкода частичного диапазона (`--from/--to`) пользователь задаёт `--offset`, иначе сдвиг обнаруживается и приводит к отказу, а не к тихому сравнению «с начала».

### Метрики кадра (MET)

- [x] **MET-01**: Для кадра считается сохранность цвета мелких насыщенных деталей любого оттенка (медиана и p10 по блокам, число блоков); при недостатке блоков — «нет мелких цветных деталей», а не число.
- [x] **MET-02**: Для кадра считаются PSNR Y/U/V глобально и худший тайл по Y и по цветности.
- [x] **MET-03**: Для кадра считаются средняя яркость в нитах (PQ EOTF), доля теней < 5 нит и сохранность детали по Y.
- [x] **MET-04**: Для кадра считается ΔE ITP (ITU-R BT.2124) — среднее и p99 по кадру.
- [x] **MET-05**: Все пороги — именованные константы конфигурации с пометкой «provisional» в отчёте.

### Кандидаты (CND)

- [x] **CND-01**: Пользователь задаёт кадры вручную (`--frames`).
- [x] **CND-02**: Худшие сцены по CSV метрик qsvencc (`ssim_y`/`psnr_y`), который пишет `enpipe encode`, становятся кандидатами (кадр внутри сцены).
- [ ] **CND-03**: Скан цвета: по одной точке внутри каждой сцены из `.scenes` (не первый кадр сцены); худшие по сохранности цвета — кандидаты.
- [x] **CND-04**: Внешний покадровый VMAF (tsv/csv, десятичная запятая, колонка `vmaf`) — необязательный вход; длина и база индекса проверяются, при несовпадении — отказ использовать файл с объяснением.
- [x] **CND-05**: Кандидаты из всех источников сливаются с разносом `--min-gap` и квотой на сцену; у каждого указано, откуда он.
- [ ] **CND-06**: Кадры, где VMAF высокий, а цвет мелких деталей потерян, помечаются отдельным флагом «VMAF хорош, цвет плох».

### Отчёт (RPT)

- [x] **RPT-01**: Отчёт `report.md`, `index.html` и `report.json` строится из одной модели данных; `report.json` стабилен и машинно-читаем.
- [ ] **RPT-02**: Для каждого кадра в `index.html`: кропы 1:1 худшего тайла и ×2 худшего цветного блока «источник | энкод», полные кадры и карта разницы — PNG без потерь, тонмаппинг PQ→SDR (`desat=0`) только для просмотра, с подписью.
- [ ] **RPT-03**: Сводка по паре: перцентили метрик (min, p1/p5/p10, медиана) по проанализированным кадрам и таблица кандидатов по убыванию серьёзности.
- [ ] **RPT-04**: Упавшее извлечение кадра видно в отчёте строкой ошибки, а не пропадает.

### Сравнение энкодов (CMP)

- [ ] **CMP-01**: Пользователь сравнивает два энкода одного источника (`--compare <enc2>` или дельта двух `report.json`) и видит рядом сохранность цвета мелких деталей (медиана/p10), PSNR U/V, ΔE ITP и битрейт на одних и тех же кадрах.

### Калибровка (CAL)

- [ ] **CAL-01**: Пороги проверены минимум на трёх материалах (тёмный, светлый, зернистый/анимация) и на синтетике с известной потерей; контроли: энкод против себя = 100 %, `--icq 1` — пол шума.
- [ ] **CAL-02**: Приёмка на известных данных: синтетика handoff даёт 71 % → 88 % при `--av1-chroma-delta-q -32` (vppsync9); E01 кадр 66490 и участок 3:56–4:48 попадают в отчёт.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Единая оценка качества 0–100 | Прячет конкретные проблемы, ради которых делается отчёт |
| Метрики на тонмаппленном SDR | Тонмаппинг клиппит насыщенный цвет и сжимает тени — для метрик недопустим, только для глаз |
| HDR-VDP-3 / ColorVideoVDP встроенно | Новые тяжёлые зависимости (Matlab/PyTorch) |
| Автоподбор ICQ / автоперекодирование проблемных сцен | Решения оставляем человеку; analyze только диагностирует |
| Покадровый анализ всего файла | Дорого на 4K/HDD; кандидаты + скан по сценам дают то же |
| Веб-вьюер / JS в отчёте | Статичный HTML достаточен |
| Изменения пути кодирования | Корректность энкода — core value; analyze изолирован |
