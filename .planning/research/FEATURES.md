# Feature Research

**Domain:** офлайн-анализ качества AV1-энкода HDR10 PQ (CLI-отчёт `enpipe analyze <src> <enc>`)
**Researched:** 2026-10-05
**Confidence:** MEDIUM (определения метрик и поведение av1an/ab-av1/libvmaf подтверждены источниками; применимость к 4K-кадрам по скорости и точное наличие `xpsnr` в сборке BtbN n9.0.2 не проверялись на месте)

Область: только НОВЫЕ функции v1.3. Путь кодирования не затрагивается. Всё описание ниже, кроме идентификаторов, на русском.

## Как устроены такие инструменты (кратко)

Инструменты оценки качества энкода делятся на три класса.

1. **Агрегаторы одной цифрой** (ab-av1, `ffmpeg -lavfi libvmaf`, ffmetrics). Считают метрику (обычно VMAF) по всему файлу или по семплам, сводят в одно число (mean, harmonic mean, перцентиль) и принимают решение «годится / не годится». ab-av1 `crf-search` режет видео на 20-секундные семплы через равные интервалы (по умолчанию `--sample-every 12m`), кодирует каждый, считает VMAF и предсказывает итог по среднему. Это инструмент подбора CRF, а не диагностики: он отвечает «какой CRF», а не «где плохо».
2. **Пер-чанковые зонды** (av1an target-quality). Для каждого чанка (сцены) делает пробные энкоды, снимает покадровый VMAF и сводит его перцентилем: по умолчанию `--probing-stat percentile=1`, т.е. 1-й перцентиль, а не среднее, чтобы худшие кадры сцены определяли вердикт. Единица отбора там — чанк. Это ровно та же гранулярность, что у enpipe (сцена из `.scenes`).
3. **Отчёты о худших кадрах** (стиль Netflix, libvmaf json). `libvmaf` с `log_fmt=json` отдаёт массив `frames` (VMAF, PSNR, SSIM покадрово) и `pooled_metrics` (mean, harmonic_mean, min, max); в CLI `vmaf` есть `--pool` с `mean|harmonic_mean|median|min|perc5|perc10|perc20`. Типовой отчёт: сортировка кадров по возрастанию метрики, N худших, кропы источник/энкод рядом, график метрики по времени.

Отсюда следуют ожидания пользователя от офлайн-отчёта: сводка по метрикам с перцентилями (не только mean), ранжированный список худших мест с таймкодами и номерами кадров, визуальные пары источник/энкод, воспроизводимость (какие кадры и почему выбраны). Ни один из аналогов не смотрит на цвет мелких деталей: VMAF считается по Y, а PSNR/SSIM-сводки по U/V усредняют по всему кадру и прячут локальную потерю (в handoff: PSNR U/V 54.9/55.6 дБ при 30-50% потери насыщенности мелких деталей). Это и есть пространство для дифференциации enpipe.

## Метрики: что практично на numpy без новых зависимостей

В проекте уже есть numpy 2.5.1, ffmpeg n9.0.2 и (опционально, внешний) VMAF. Критерий практичности: считается по сэмплированным кадрам (сотни, не все 100k), в numpy, без torch/CUDA/Matlab.

| Метрика | Определение / источник | Практично в numpy? | Вердикт для enpipe |
|---------|------------------------|--------------------|--------------------|
| PSNR/SSIM по U и V | Классика; PSNR_UV по плоскостям Cb/Cr 10 бит. qsvencc уже пишет SSIM/PSNR в CSV по сценам | Да, тривиально | Включить, но как **вспомогательную** метрику: глобальное усреднение скрывает локальные потери (см. handoff) |
| Локальный PSNR/MSE U/V по тайлам, худший тайл | Та же формула на окнах (например 16x16 chroma); берётся минимум/перцентиль по тайлам | Да, reshape + mean | Включить: дёшево и ближе к цели, чем глобальный PSNR. То же для Y: «худший тайл по Y» (уже в целевых фичах milestone) |
| ΔE_ITP (ITU-R BT.2124) | ΔE_ITP = 720·sqrt(ΔI² + ΔT² + ΔP²), где I, T, P — компоненты ICtCp (BT.2100, PQ) с T = 0.5·Ct. Единица ≈ 1 JND на единицу (порог видимости около 1). Источник: [ITU-R BT.2124-0](https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.2124-0-201901-I!!PDF-E.pdf), [Portrait Displays обзор](https://www.portrait.com/resource-center/eitp-is-now-itu-r-bt-2124-is-the-industry-ready-to-move-on-from-e2000/) | Да: YCbCr→RGB (BT.2020 NCL) → линейный RGB через PQ EOTF → LMS матрицей 3x3 → обратный PQ → I/Ct/Cp. Только поэлементные операции и две матрицы 3x3 | **Главный кандидат** на «цветовую» метрику: стандартизован именно для HDR/WCG, работает в абсолютных нитах, не требует тонмаппинга. Считать по сэмплированным кадрам, пулить перцентилями и по тайлам. Константы матриц брать строго из BT.2100/BT.2124 (в сводке автор не сверял числа, проверить при реализации — LOW для самих констант) |
| CIEDE2000 на тонмаппленном | ΔE2000 в CIELAB над SDR-картинкой | Формула реализуема в numpy (около 40 строк), но результат зависит от выбранного тонмаппинга и белой точки; не стандартен для HDR (ΔE_ITP введён именно как замена, [SMPTE 2019 сессия](https://2019.smpte.org/home/session/162191/%CE%94eitp-is-now-itu-r-bt-2124-is-the-industry-ready-to-move-on-from-%CE%94e2000)) | Не делать основной метрикой. Тонмаппинг PQ→SDR нужен для **кропов в отчёте** (человеку), а не для измерения |
| Метрика «сохранность цвета мелких деталей» (домашняя) | Проекция энкодных (Cb,Cr) на источник в блоках 16x16 chroma-отсчётов с 3..20 насыщенными отсчётами; медиана и 10-й перцентиль по блокам (`measure_red.py`, handoff §2) | Да, numpy + ffmpeg | **Ключевой дифференциатор.** Нет аналога в литературе; валидирована на E01 (кадр 66490, участок 3:56–4:48). Нужно обобщить с «красного» (Cr−Cb) на любое направление насыщенности, иначе слепа к синему/зелёному |
| XPSNR (Fraunhofer HHI) | Блочно-взвешенный PSNR, считается раздельно для Y, U, V; разработчики рекомендуют минимум из трёх как итог, сообщество часто берёт (4·Y+U+V)/6. Источник: [fraunhoferhhi/xpsnr](https://github.com/fraunhoferhhi/xpsnr), [x266 wiki](https://wiki.x266.mov/docs/metrics/XPSNR) | Не в numpy, но это штатный фильтр ffmpeg (в mainline с 7.1; см. [документацию 8.0](https://ayosec.github.io/ffmpeg-filters-docs/8.0/Filters/Video/xpsnr.html)); новых зависимостей нет, нужно проверить наличие в BtbN n9.0.2 (MEDIUM) | Опционально, P3. Даёт per-plane числа, но остаётся глобальным по кадру и также размывает мелкие детали; не заменяет локальную метрику |
| HDR-VDP-3 | Модель зрительной системы для HDR ([arXiv 2304.13625](https://arxiv.org/pdf/2304.13625)) | Нет: Matlab-реализация (есть Octave/порты, но тяжёлые) | Anti-feature для v1.3: новая зависимость, медленно |
| ColorVideoVDP (cvvdp) | Первая цветовая пространственно-временная VDP; SIGGRAPH 2024, Mantiuk et al., [arXiv 2401.11485](https://arxiv.org/pdf/2401.11485); поддерживает PQ HDR через `--display standard_hdr_pq`, пакет `cvvdp` на [PyPI](https://pypi.org/project/cvvdp/) | Нет: PyTorch (torch в зависимостях), на GPU не Arc-дружественно, минуты на кадр/секунду 4K на CPU | Anti-feature для v1.3 (нарушает «без новых зависимостей»). Подходящий кандидат в backlog как **внешний опциональный** валидатор для 5–10 кадров-кандидатов, чтобы проверить, что домашняя метрика согласуется с признанной моделью |

Вывод по практичности: в numpy реализуемы и достаточны четыре вещи: PSNR/MSE U/V (по тайлам), ΔE_ITP, домашняя метрика мелких цветных деталей, структурные локальные метрики Y. VMAF остаётся внешним входом (`.json` от libvmaf, уже решено в milestone). HDR-VDP/ColorVideoVDP тянут тяжёлые зависимости и не нужны для обнаружения проблемы, которая уже локализована простой метрикой.

## Как инструменты выбирают кандидатов-кадры

| Подход | Кто так делает | Суть | Применимость к enpipe |
|--------|----------------|------|------------------------|
| Равномерный семплинг по времени | ab-av1 (`--sample-every`, 20 с семплы) | Дёшево, но худшие места легко пропустить | Недостаточно: проблемный фрагмент в E01 занял минуты из 46+ |
| Пер-чанковый пул перцентилем по покадровой метрике | av1an (`percentile=1`) | Единица = сцена; решает худший хвост кадров | Подходит: сцены уже есть в `.scenes`, в CSV qsvencc есть per-scene SSIM/PSNR |
| Ранжирование кадров по покадровой метрике (min/perc5), N худших | libvmaf json + `--pool`, Netflix-стиль отчёты | Нужен покадровый VMAF на всём файле (дорого) | Принять как внешний вход (опционально, уже в плане) |
| Скан-метрика на дешёвом признаке по всему файлу | Не типично для аналогов | Одна точка на сцену (например кадр в середине/после keyframe сцены), считается numpy-метрикой цвета | Уникальный источник кандидатов для enpipe: ловит то, что VMAF не видит, и масштабируется (число сцен, а не кадров) |
| Худшие сцены по CSV энкодера | Нет прямого аналога (SSIM/PSNR от qsvencc) | Нулевая стоимость, данные уже есть | Брать, но помнить: глобальные PSNR/SSIM прячут локальную потерю (handoff §1) |
| Ручной список кадров | Все инструменты (`--frames`, `-ss`) | Оператор знает, где смотреть | Необходим как опорный сценарий воспроизведения |

Важная деталь: кандидатов нужно **дедуплицировать и объединять** по окрестности (соседние кадры одной сцены с плохой метрикой почти идентичны) и держать квоту на сцену, иначе топ-N состоит из 20 соседних кадров одного участка. Это стандартная проблема отчётов о худших кадрах.

Согласуется с Core Value (кадры проверены) | MEDIUM | Использовать frame-count из ffprobe и `.scenes`; при расхождении громкий отказ через `die()`, не молчаливое продолжение. | Ранжированный список худших кадров/сцен с таймкодом, номером кадра, значением метрики | Суть отчёта «найди проблемные места» | LOW | Таблица в `report.md` |

| Воспроизводимость: в отчёте указаны версии инструментов, параметры, откуда кандидат (источник отбора) | Любой пост-анализ должен быть проверяем; аналогично сообщению о hash/revision qsvencc в проекте | LOW | Блок «метаданные запуска» |

### Anti-Features (часто просят, но проблематичны)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| ColorVideoVDP / HDR-VDP-3 как встроенные метрики | «Самые точные» перцептивные модели | Тянут PyTorch/Matlab, нарушают «без новых зависимостей», медленны на 4K; результат трудно интерпретировать без калибровки дисплея и расстояния | Домашняя метрика + ΔE_ITP; cvvdp как внешний ручной валидатор для 5–10 кадров (backlog) |
| Собственный VMAF (сборка libvmaf, кодирование/пересчёт) в v1.3 | «Всё в одном инструменте» | Уже явно в backlog; тяжёлая сборка, шумный на 4K HDR (модель SDR vmaf_4k_v0.6.1 без тонмаппинга и так вне домена) | Принимать внешний json; сфокусироваться на том, чего VMAF не видит |
| Одно итоговое «качество 0–100» на файл | Простота вердикта pass/fail | Нивелирует локальные дефекты — ровно та ошибка, что мотивировала milestone; «оценка» без калибровки вводит в заблуждение | Ранжированные кандидаты + перцентили по метрикам; пороги только как подсветка, не вердикт |
| Метрики на тонмаппленной SDR-картинке как основные (CIEDE2000, SSIM на тонмапе) | Привычные инструменты и пороги | Результат зависит от тонмаппера и яркости; ошибка тонмаппера смешивается с ошибкой энкодера | Метрики в PQ/ICtCp; тонмап только для визуализации |
| `--analyze` внутри `encode`/`run` | Один шаг вместо двух | Уже вынесено в backlog; повышает риск для пути кодирования (Core Value: корректность энкода неприкосновенна) и удлиняет прогон на HDD | Отдельная команда `analyze`, вызываемая после; интеграция позже |
| Покадровая метрика по всем кадрам файла | «Полнота» | Для 4K и 100k+ кадров на CPU numpy — часы; ZFS на вращающихся дисках дополнительно душит чтение | Одна точка на сцену + уточнение вокруг худших; полный VMAF — внешний вход |
| Автоматическое исправление/перекодирование проблемных сцен | Логичное продолжение «нашёл — исправил» | Затрагивает путь кодирования, чанки и счётчики кадров (Core Value); ограничение сейчас в энкодере (handoff), не в параметрах enpipe | Отчёт и рекомендации; правка после того, как форк даст `--av1-chroma-delta-q` |
| Интерактивный веб-вьюер, серверная часть, БД результатов | «Красивее» | Вне scope (локальный CLI/NAS, никаких сервисов) | Статический `index.html` с `<img>` и ссылками на кропы |
| Автоподбор CRF/ICQ по метрике (как ab-av1/av1an target-quality) | Знакомый паттерн | Другая задача (управление энкодом, не анализ); по handoff снижение ICQ даёт ×3–5 по битрейту ради +2–5 п.п., то есть неэффективно для цвета | Не в v1.3 |

## Feature Dependencies

```
Проверка выравнивания ──requires──> ffprobe frame count + `.scenes` (есть)
    └──requires──> Извлечение пар кадров по номеру (shared.proc, ffmpeg select/setpts)

Метрики кадра (U/V по тайлам, худший тайл Y, ΔE_ITP, сохранность мелких деталей)
    └──requires──> Извлечение пар кадров (10-бит YUV → numpy)
    └──requires──> Проверка выравнивания (иначе метрики недостоверны)

Скан цвета (1 точка на сцену) ──requires──> `.scenes` (scenes_io.py, есть) + метрика сохранности цвета
Худшие сцены по CSV ──requires──> metrics CSV qsvencc (encoding/metrics.py, есть)
Внешний VMAF ──requires──> парсер libvmaf json (опционально)
Ручной список кадров ──requires──> только извлечение пар кадров

Единый ранжированный список кандидатов ──requires──> любые источники кандидатов + дедупликация

Кропы + тонмап PQ→SDR ──requires──> Извлечение пар кадров
report.md / index.html / report.json ──requires──> единый ранжированный список + кропы

Расхождение «VMAF хорош / цвет плох» ──enhances──> отчёт (требует внешний VMAF + метрика цвета)
Обобщение метрики на любые направления насыщенности ──enhances──> метрика сохранности мелких деталей
Сравнение «до/после» ──enhances──> report.json (дельта двух прогонов)

Встроенный VMAF / cvvdp ──conflicts──> «без новых зависимостей»
`--analyze` в encode/run ──conflicts──> неприкосновенность пути кодирования
```

### Dependency Notes

- **Метрики требуют выравнивания:** при расхождении числа кадров или сдвиге PTS попарные метрики бессмысленны, а молчаливый мусор противоречит Core Value; сначала проверка и громкий отказ.
- **Скан цвета требует `.scenes`:** без файла сцен нужно либо запускать `enpipe detect`, либо деградировать на фиксированный шаг; решить на этапе планирования (рекомендация: требовать `.scenes`, при отсутствии предлагать детект, а не молча считать).
- **Дедупликация предшествует рендерингу:** кропы дорогие; их нужно делать только для финального списка.
- **Frame-number discipline:** все источники кандидатов должны разговаривать номерами кадров (VMAF json идёт по номерам кадров, CSV — по сценам, ручной список — по номерам).

## MVP Definition

### Launch With (v1.3)

- [ ] `enpipe analyze <src> <enc>` для файла и папки (пары `<stem>.Encoded.mkv`) — основная точка входа
- [ ] Проверка выравнивания (frame count, PTS) с громким отказом — без неё всё остальное недостоверно
- [ ] Извлечение пар кадров по номеру, 10-бит YUV в numpy через `shared.proc`
- [ ] Метрика «сохранность цвета мелких деталей» (обобщённая) + PSNR/MSE U/V по тайлам и худший тайл Y
- [ ] Скан цвета по сценам из `.scenes` и ручной список кадров как источники кандидатов
- [ ] Единый список кандидатов с дедупликацией и квотой на сцену
- [ ] `report.md` + `index.html` с кропами источник/энкод и тонмаппингом PQ→SDR; `report.json`
- [ ] Худшие сцены по CSV qsvencc как источник кандидатов (стоимость около нуля)

### Add After Validation (v1.3.x)

- [ ] ΔE_ITP как независимое подтверждение — после того, как метрика мелких деталей проверена на E01 и синтетике; триггер: нужна стандартная метрика для обоснования порогов
- [ ] Внешний покадровый VMAF (`--vmaf-json`) и флаг «VMAF хорош / цвет плох» — триггер: у оператора уже есть json
- [ ] Метрики ниты/доля теней и «сохранность детали» Y — триггер: подозрения на теневые дефекты
- [ ] Режим сравнения двух энкодов (дельта) — триггер: выход `--av1-chroma-delta-q` из форка (`8.32-vppsync9`)

### Future Consideration (v2+)

- [ ] XPSNR через ffmpeg как дополнительный столбец — незначительная ценность сверх локальных метрик
- [ ] cvvdp как внешний валидатор для небольшого числа кадров — если потребуется калибровка порогов

## Зависимости от существующего кода (для роадмапа)

| Нужно | Где уже есть | Замечание |
|-------|--------------|-----------|
| Парсинг `.scenes` | `src/enpipe/encoding/scenes_io.py` | Читать как есть; формат `scene NNNN frames [S, E) T0 .. T1` |
| Запуск ffmpeg/ffprobe | `src/enpipe/shared/proc.py` (`run`/`popen`) | Никаких прямых `subprocess.*`; тесты через pytest-subprocess |
| Пакетная итерация по файлам | `src/enpipe/shared/batch.py` | Для режима папки |
| Логирование и выход | `src/enpipe/shared/logging.py` (`log`, `step`, `die`) | Сообщения на русском |
| CSV метрик qsvencc | `src/enpipe/encoding/metrics.py` | Источник «худших сцен» |
| HDR-метаданные (mastering display, max CLL) | `src/enpipe/encoding/hdr.py` | Для PQ→нит и тонмаппинга кропов |
| CLI-диспетчер | `src/enpipe/cli/main.py` | Новый подкоманд `analyze` |
| numpy | уже в зависимостях (2.5.1) | Единственная вычислительная библиотека для новых метрик |
| Конфиг через frozen dataclass | соглашение `DetectionConfig` | `AnalyzeConfig` по тому же образцу |
