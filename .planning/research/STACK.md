# Technology Stack — v1.3 `enpipe analyze`

**Project:** enpipe
**Milestone:** v1.3 Анализ качества энкода
**Researched:** 2026-10-05
**Scope:** только добавления под `enpipe analyze`. Python 3.12, numpy 2.5.1, ffmpeg/ffprobe BtbN n9.0.2, `shared.proc`, pytest-тиры не пересматриваются.

## Вывод одной строкой

Новых runtime-зависимостей нет. Всё делается так: **ffmpeg (rawvideo → stdout) → numpy** для метрик, **ffmpeg `zscale`+`tonemap` (CPU)** для SDR-кропов PNG, **stdlib (`zlib`/`struct`, `html.escape`, f-строки)** для PNG-карт и HTML. libvmaf уже в бинарнике вместе с моделями, но в v1.3 не используется (backlog).

Проверено локально на `ffmpeg n9.0.2-22-g46d8f462ee-20261001` (тот же `/usr/local/bin/ffmpeg`, что в образах). Помечено HIGH, если запускалось здесь или есть в `-filters`/`-h`; MEDIUM, если рассуждение по документации или по одному эксперименту.

## 1. Извлечение кадров 10-бит YUV из mkv

### Рекомендация

| Что | Решение | Почему |
|-----|---------|--------|
| Формат вывода | `-f rawvideo -pix_fmt yuv420p10le -` в stdout, `np.frombuffer(buf, '<u2')` | Проверено: размер буфера = W*H*3/2*2 байт, значения 0..1023, без потерь и без промежуточных файлов. Плоскости Y, затем U, затем V, нарезаются срезами numpy |
| Декод | Программный (`-hwaccel` не нужен) для одиночных кадров; `--avhw`-подобный QSV-путь не использовать | Для analyze важна точность, а не скорость. Программный HEVC/AV1 (libdav1d) побайтно совпадает с QSV (по handoff: «HEVC через QSV и программный декодер дают побайтно одинаковый кадр»). Не занимает GPU, который нужен энкоду. Не требует `/dev/dri` |
| Запуск | Только через `enpipe.shared.proc.run()`/`popen()` | Правило проекта, единый шов для pytest-subprocess |
| Параллелизм | `ThreadPoolExecutor`, один ffmpeg на кадр (по паттерну проекта) | Работа в подпроцессах, GIL не мешает |

Ограничение: `yuv420p10le` предполагает 4:2:0 10-бит. Для 8-бит источников брать `yuv420p` и `'u1'`; формат определять по `ffprobe pix_fmt` (уже есть `probe_source`). Не конвертировать в RGB для метрик: U/V-метрика (Cr−Cb красноты, retention) должна считаться в исходных 10-бит отсчётах, как в `measure_red.py` из handoff.

### Точный seek: как не ошибиться на кадр

Ситуация: mkv хранит pts с TimestampScale 1 мс, у 23.976 к/с кадры лежат в 0, 42, 83, 125, ... мс (ffprobe показал 0.042, 0.083, 0.125). Время `N*1001/24000` на кадре не совпадает с записанным pts.

Проверено (HIGH для данного бинарника, 54 кадра из 480 на HEVC 23.976, 1 мс): входной `-ss T -i file -frames:v 1` с точным `T=N*1001/24000` дал верный кадр на всех проверенных N, то есть сломаться он не обязан. Но это зависит от направления округления pts в muxer'е (вниз → кадр N уйдёт в N+1, т.к. `-ss` оставляет кадры с pts ≥ T). Поэтому правила:

1. **Сдвигать цель на половину кадра назад:** `-ss (pts_N − half_frame_duration)`. Тогда кадр N-1 заведомо отсекается (его pts < цель), а кадр N заведомо проходит независимо от ms-округления. Проверено на тех же 54 кадрах: 0 ошибок.
2. **Брать pts_N из таблицы, а не из `N/fps`:** один раз `ffprobe -select_streams v -show_entries packet=pts_time -of csv=p=0`, отсортировать по возрастанию (порядок пакетов — decode order, не display, у B-кадров pts не монотонны: наблюдали 0, .083, .042, .209...). Индекс N в отсортированном списке и есть номер кадра в презентационном порядке. Это даёт корректность на VFR и на источниках с ненулевым `start_time` (backlog 999.6), где `N/fps` ошибётся. `half = (pts[N] − pts[N−1])/2`; для N=0 просто `-ss 0` или без `-ss`.
3. **Парная проверка выравнивания:** pts таблицы src и enc сравнивать по индексу (с допуском ±1 мс на округление) до всякого извлечения; расхождение числа пакетов или pts — это и есть «проверка выравнивания» из требований. Дёшево и не требует декода.
4. **Страховка после извлечения:** запрашивать `-frames:v 1` и `-f framemd5`-проверку не нужно. Вместо этого в тестах сравнивать извлечённый кадр с кадром, полученным последовательным декодом (`framemd5` всего файла) на синтетике. Этот приём использован здесь.
5. **Не использовать** `-ss` как выходную опцию (после `-i`): декодирует файл от начала, на 3840×1600 HEVC по HDD это минуты на кадр.
6. **Не использовать** `select='eq(n,N)'` на всём файле для одиночных кадров по той же причине. Допустим только для пакетной выборки многих кадров из одной сцены: seek на ключевой кадр перед сценой + `select` по `n` относительно него. Номер `n` после `-ss` сбрасывается, это существующий нюанс детектора (см. `stream.py`, `-copyts`). При `-copyts` выражение в `select` использует `TB` в верхнем регистре (`gte(pts*TB,...)`); `tb` в нижнем регистре даёт ошибку парсинга (проверено).
7. Опорный источник для маппинга кадров «src кадр N ↔ enc кадр N» опирается на уже проверяемый инвариант pipeline: число кадров равно, кадры идут в том же порядке. Если analyze увидит разное число кадров, остановиться с `die()` и отчётом, а не угадывать смещение.

Confidence: HIGH на поведении ffmpeg, MEDIUM на «ms-округление может сломать точный T» (не воспроизведено, механизм известен из семантики `-ss`). Правило полкадра безопасно в обоих случаях.

## 2. PQ → SDR тонмаппинг для PNG-кропов

### Рекомендация: `zscale` + `tonemap` (CPU), не `libplacebo`

| Критерий | zscale+tonemap | libplacebo | tonemap_opencl / tonemap_vaapi |
|----------|----------------|------------|-------------------------------|
| Есть в n9.0.2 | да (`-filters`: `zscale`, `tonemap`) | да (в сборке `--enable-libplacebo`) | да |
| Нужен GPU/драйвер | нет | **Vulkan-устройство** | OpenCL / VA-API |
| Работает в контейнере сейчас | **да, проверено**: 0.13 с на кадр 640×360, PNG получен | **нет**: `VK_ERROR_INCOMPATIBLE_DRIVER`, ICD в образах не установлен (в обоих Dockerfile нет vulkan/mesa) | зависит от драйвера, лишняя связность с GPU |
| Детерминизм | да (CPU, фиксированная математика) | зависит от драйвера и peak detection (`peak_detect=true` по умолчанию меняет результат по кадрам) | зависит от драйвера |
| Эстетика | достаточна для ревью (hable/mobius) | лучше (bt.2390, gamut mapping) | средне |
| Риск для Arc во время энкода | нет | занимает GPU и нужен доп. пакет `mesa-vulkan-drivers` | занимает GPU |

Почему так: PNG нужны оператору для сравнения «src vs enc» глазами. Важна одинаковая обработка обеих сторон и воспроизводимость, а не лучший тонмаппинг. libplacebo потребовал бы добавить `mesa-vulkan-drivers` в оба образа и проверять Vulkan на A380 для косметического выигрыша; в этом окружении он не инициализируется вообще. Это вынос в backlog («libplacebo-режим», связан с 999.5).

### Рабочая цепочка (проверена, выдала PNG)

```
zscale=t=linear:npl=203,format=gbrpf32le,zscale=p=bt709,
tonemap=hable:desat=0,
zscale=t=bt709:m=bt709:r=pc,format=rgb24,
crop=W:H:X:Y,scale=iw*4:ih*4:flags=neighbor
```

Пояснения:
- `npl=203`: опорный белый HDR (диффузный белый 203 нит по BT.2408); 100 даёт слишком тёмную картинку, 1000 перегружает яркие области. Вынести в параметр отчёта, по умолчанию 203. (MEDIUM: значение из BT.2408, визуально не калибровалось на реальном материале.) Входные теги цвета (`smpte2084`, `bt2020nc`) zscale берёт из потока; если контейнер их не несёт, явно задать `tin=smpte2084:min=bt2020nc:pin=bt2020`.
- `tonemap` принимает значения: none, linear, gamma, clip, reinhard, hable, mobius (проверено `-h filter=tonemap`). По умолчанию `none`, поэтому `tonemap=hable` указывать обязательно. `desat=0` убирает десатурацию ярких областей: иначе искусственно обесцвечивается именно то, что мы сравниваем (цвет мелких деталей).
- `format=gbrpf32le` между `zscale` обязателен: `tonemap` работает на float-линейном RGB.
- `scale=...:flags=neighbor` для увеличения кропов без сглаживания, чтобы пиксели реально были видны.
- Одну и ту же цепочку применять к src и enc; кроп делать после тонмаппинга (или `crop` в начале цепочки по YUV, что быстрее на 3840×1600: кроп по чётным координатам до `zscale` сокращает работу в десятки раз). Рекомендуется crop первым, с чётными X/Y/W/H из-за 4:2:0.
- Для SDR-источников тонмаппинг пропускать (определять по `color_transfer` из `probe_source`/`hdr.py`).
- Dolby Vision profile 5 (IPT-PQ-C2) этой цепочкой отобразится неверно. Это известное ограничение, для P5 пометить кадр в отчёте и не тонмапить (999.5).

### Числа «ниты/тени»

Считать в numpy из 10-бит Y: ST 2084 EOTF (константы m1, m2, c1, c2, c3 из стандарта), `nits = 10000 * EOTF(Y_norm)`; для limited range сначала `(Y−64)/876`. Никаких библиотек. Это ровно та арифметика, что в прототипе `vmaf_frames.py`. Confidence HIGH (стандарт SMPTE ST 2084).

## 3. libvmaf в n9.0.2: модели и использование (на будущее)

Проверено (HIGH):
- Фильтр `libvmaf` собран (`--enable-libvmaf`), опции `model`, `feature`, `log_path`, `log_fmt`, `n_threads`, `pool`.
- **Модели вшиты в бинарник** (строки в бинарнике): `vmaf_v0.6.1`, `vmaf_4k_v0.6.1`, `vmaf_v0.6.1neg`, `vmaf_4k_v0.6.1neg`, `vmaf_float_v0.6.1`, `vmaf_float_4k_v0.6.1`, `vmaf_float_v0.6.1neg`, `vmaf_float_b_v0.6.3`. Внешние `.json`-файлы и `model=path=` не нужны: `model=version=vmaf_4k_v0.6.1`.
- Рабочая команда (запущена на двух yuv420p10le): 

```
ffmpeg -i enc.mkv -i src.mkv -lavfi \
 "[0:v][1:v]libvmaf=model=version=vmaf_4k_v0.6.1:log_fmt=csv:log_path=v.csv:n_threads=4:feature=name=psnr" -f null -
```

- Первый вход = дистордированный (энкод), второй = референс. Порядок важен.
- CSV покадровый, колонка `Frame` с нуля, содержит `psnr_y, psnr_cb, psnr_cr` (при `feature=name=psnr`), `vmaf`, `integer_vif_scale*`, `integer_adm2`, motion. Это значит, что **PSNR по U/V покадрово можно получить тем же проходом**.
- Нумерация: `libvmaf` csv считает кадры с 0, а `psnr=stats_file` (`n:`) с 1. Не смешивать без нормализации.
- Для 4K-материала (3840×1600, ширина 3840) подходит `vmaf_4k_v0.6.1`; для ≤1080p `vmaf_v0.6.1`. Модель задаёт ожидаемый размер просмотра; при смене модели числа несопоставимы с внешним CSV.
- Для v1.3 **не добавлять**: внешний VMAF-CSV остаётся опциональным входом (формат прототипа). Встроенный запуск libvmaf отнесён в backlog. VMAF считается только по Y, и именно поэтому он не видит потерю цвета (handoff). Если понадобится, подключать через `shared.proc`, парсить CSV через stdlib `csv`.
- Парсер входного CSV должен быть терпимым к разным колонкам: внешние инструменты (Netflix `vmaf` CLI, ffmpeg csv, json) выдают разные схемы. Для v1.3 принять CSV с колонками `Frame`/`frame` и `vmaf`; JSON отложить.

### Альтернатива без libvmaf для U/V

Фильтр `psnr=stats_file=...` (есть, проверено) даёт `psnr_u`/`psnr_v` покадрово и `ssim` аналогично; но PSNR средний по кадру и мелкие детали не покажет (в handoff 54.9/55.6 дБ при потере цвета). Поэтому U/V-диагностика остаётся блочной, на numpy.

## 4. Запись PNG без Pillow

Два проверенных пути, оба без зависимостей:

| Назначение | Путь | Почему |
|------------|------|--------|
| Тонмапнутые кропы src/enc из видео | ffmpeg напрямую: `-frames:v 1 out.png` с цепочкой из §2. Результат проверен: PNG создан | Кроп, тонмаппинг и увеличение за один проход; numpy не нужен |
| Картинки, нарисованные в numpy (карты худших тайлов, тепловые карты красноты, разности) | **stdlib-писатель PNG**: `zlib.compress` + `struct.pack` + `zlib.crc32` (≈10 строк, 8-бит RGB/gray, фильтр 0). Проверено: ffmpeg читает такой файл без ошибок | Не нужно запускать ffmpeg под каждую картинку и нет зависимости |
| (запасной) numpy → rawvideo → ffmpeg | `-f rawvideo -pix_fmt rgb24 -s WxH -i - -frames:v 1 out.png`; энкодер `png` поддерживает rgb24, rgb48be, gray, gray16be, pal8, ya8 | Годится, если нужен `scale`/`neighbor` увеличение над numpy-массивом. Идёт через `shared.proc.popen` |

Чего не делать: добавлять Pillow/matplotlib/imageio. Это нарушает «только numpy» и раздувает runtime-образ ради 10 строк. PNG пишется с `compress_level` по умолчанию; для кропов размером в сотни пикселей этого достаточно.

Сторона размещения кропов в отчёте: `src` и `enc` рядом через две отдельные PNG и CSS-сетку, а не через `hstack` в ffmpeg. Так проще кэшировать и перезапускать.

## 5. HTML-отчёт без шаблонизатора

Рекомендация: **f-строки + `html.escape` + `pathlib`**, один модуль `report_html.py` с функциями, возвращающими строки. Без Jinja2.

- Стили: один встроенный `<style>` (CSS grid для пар src|enc, `image-rendering: pixelated` для увеличенных кропов). Никакого JS; максимум `<details>` для сворачивания кадров.
- Изображения: относительные ссылки на PNG рядом с `index.html` (каталог отчёта переносим). Не вшивать base64: файл раздувается, а PNG-кропов будут десятки.
- Экранирование: все строки из внешних источников (имена файлов, поля CSV) через `html.escape`; числа форматировать до подстановки.
- `report.md` генерируется из того же объекта-модели результатов (dataclass(frozen=True) по соглашению проекта), что и HTML, чтобы не расходились.
- Цвет и таблицы: `<table>` с классами `ok/warn/bad` по порогам. Не использовать JS-графики. Если нужна визуализация по времени, писать inline-SVG (`<polyline>`) строкой; это 20 строк и без зависимостей.
- Язык: комментарии, логи, заголовки отчёта на русском, идентификаторы на английском (соглашение проекта).
- Тесты: чистые функции «модель → строка», проверка на `html.escape` инъекции и на наличие ожидаемых ссылок. Относится к быстрому тиру.

## Интеграция

- Все вызовы ffmpeg/ffprobe через `enpipe.shared.proc`; тесты через `fp` (pytest-subprocess) в быстром тире. Аргументы тонмаппинга и seek строятся чистыми функциями и проверяются без запуска.
- Тест на реальном ffmpeg (без GPU) допустим как «медиа-тест» среднего тира на синтетике 640×360 (2-3 сек), как делалось здесь: проверка «seek с полкадра == кадр последовательного декода (`framemd5`)» и «PNG создан».
- Hardware-тир для analyze не нужен: ни один из выбранных путей не использует `/dev/dri`. Это важный плюс: analyze можно запускать параллельно с энкодом, не отбирая у него GPU.
- Источник кандидатов qsvencc CSV уже есть (`encoding/metrics.py`); analyze читает его как есть.
- Ограничение процесса на 3840×1600: кадр 10-бит 4:2:0 = 18.4 МБ; кроп/метрики держат в памяти один-два кадра на поток. При `JOBS=3` это десятки МБ; ограничений не требуется.
